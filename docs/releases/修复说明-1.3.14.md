# ObsidianDrop 1.3.14 修复说明

版本 1.3.14（构建 18）｜2026-11-04

## 一句话

**文字其实早就转出来了，是「交给界面」这一跳把结果弄丢了，而丢之前录音已经被删。**
1.3.14 把顺序倒过来：先落盘，再交付；投递不再依赖会话是否还活着。

## 现场日志读出来的事实

用户给的日志（MacBookPro17,1 / macOS 26.5 / 1.3.13）：

```
[21:26:04] run 1 ｜ 录音启动成功：录音-20261104-212604.caf
[21:27:38] run 1 ｜ 录音结束：墙钟 94.3s，文件 94.2s，18090496 字节，帧 4521600，写失败 0 次，峰值 90%
[21:27:39] 识别完成：用时 0.2s，已出 0 字
[21:27:41] 收尾：用时 2.9s（限 15s），正常，字数 51
[21:27:42.029] run 1 ｜ 转写返回：3.4s，音频 94.2s → 51 字
[21:27:42.030] run 1 ｜ 交付结果到主线程（done）

...  150 秒心跳，状态一直「转写中｜收尾中」...
[21:30:12] run 1 ｜ 看门狗：150 秒无事件，强制恢复界面
```

| 结论 | 依据 |
|---|---|
| 麦克风采集正常 | 94.2 秒、4521600 帧、18 MB、写失败 0、峰值 90% |
| 转写成功 | 51 字，收尾 2.9 秒正常 |
| **断点在交付** | 「交付结果」和「丢弃 done」落在同一毫秒 |
| 回收不了 | 文字在任务局部变量里，录音在交付前已被删，进程内没有任何副本 |

## 根因（四条，前三条都是「顺序」问题）

### P0-1 结果投递挂在一个随时会死的对象上

`MemoSession.emit` 原来写的是：

```swift
DispatchQueue.main.async { [weak self] in
    guard let self else { DiagLog.round(runID, "丢弃 \(what)：录音会话已释放"); return }
    ...
}
```

`self` 是 `MemoSession`。它在 `endMemo()` 里被置空，转写任务闭包一返回，这份强引用就没了。
**排在主队列里的那块闭包是在任务返回之后才执行的**，取到的 `self` 已经是 nil。
日志里两条落在同一毫秒（42.030）正是这个时序——不是「会话被提前释放」，而是「投递本来就晚于释放」。

结论：会话活多久只该决定「进度画不画得出来」，**结果能不能送到不能挂在它身上**。
1.3.14 新增 `MemoDelivery.post`：入队时取出 sink 并强持有，与产生回调的对象彻底解耦。

### P0-2 先删录音、后投递

```swift
if r.text.isEmpty { o.recordingPath = audio.path } else { store.discard() }   // ← 先删
self.emit("done") { ... }                                                     // ← 后交
```

投递一失败，**文字和录音同时消失**。用户拿到的只有一个「卡住了」的弹窗。
现在反过来：录音一律留着，笔记写成功之后才删。

### P0-3 结果没有第二份

文字只存在于一个局部变量里。进程退出、会话释放、投递被拦——任何一种都会让它彻底消失。

现在：转写完成 → **先原子落盘到待归档队列**（`~/Library/Application Support/ObsidianDrop/pending/<UUID>.json`，写完 `.tmp` 再 rename，权限 0600）→ 再去交付。
界面只是消费者之一，不是保管人。

### P1-4 轮次变了就等于丢弃

看门狗恢复界面后用户可能马上开始下一轮，`memoRunID` 一变，上一轮的结果就被「轮次不符」扔掉。
现在轮次不符不再丢弃，转补归档；归档用的 target / vault 是**转写开始时冻结**的那一份，不会串到新目标。

## 附带修掉的两处

| 问题 | 现象 | 修法 |
|---|---|---|
| 日志自相矛盾 | 「格式 未建立（没有任何音频块进来）」与「4521600 帧」同处一行——因为 `close()` 先把 `format` 置空，日志才读它 | 打开文件时固化 `formatSummary`，关句柄不影响 |
| 看门狗判断错 | 一律写「主线程还活着，是后台没进展」，而事实是后台早转完了 | 队列里有东西就说「是界面没收到交付」 |

另外补了 **丢字判据**：每条定稿结果记音频区间，收尾后算覆盖率与最长空白。

```
结果覆盖：3 段定稿（partial 291 条），覆盖 130.1s / 180.0s（72%），最长空白 38.9s
```

以后「94 秒只出 51 字」这种问题，看这一行就能判断是「本来就没说几句」还是「真丢了」，
不用再靠猜。注意它只提示、不判罪：长时间安静同样会拉低覆盖率。

## 现在的交付链路

```
录音/文件 → 转写 → 文字原子落盘(pending) → 投递界面 → 归档写笔记 → 删 pending + 删录音
                        ↓ 投递失败/进程退出/轮次被顶掉
                   下次启动 或 看门狗恢复时 → 补归档（同一条只写一次）
```

`MemoArchiveQueue` 用串行队列 + 「入队后重新确认 pending 还在」来保证幂等：
谁先删掉 pending 文件谁就是写成功的那一个，后到的看到文件没了直接返回，不会写出重复笔记。

## 验证（本机，无麦克风）

| 项 | 结果 |
|---|---|
| 内置自检 | 95 → **106 项全通过**（含投递生命周期、落盘读回、半截 JSON、覆盖率） |
| 隔离库回归 | **53/53** |
| 正常链路 `--ui-memo`（3 分钟音频） | 6.6s → 278 字 → 归档 → 复位，exit 0，队列清空 |
| **模拟结果交不到界面** `OBSIDIANDROP_DROP_DONE=1` | 20 秒后看门狗恢复并**从队列补写成功 1 条**，exit 0；修前这是永久卡死 |
| 模拟结果迟到 18 秒 | 先补归档、后结果到达 → 判定「已写过」→ **只有 1 篇笔记**，不重复 |
| 归档失败（库不存在） | exit 1，pending 保留（1073 字节 / 0600），录音保留 |
| 下次启动补归档 | 启动日志「发现 1 条待归档结果」→ 补写成功 → 队列清空 |
| 录音格式日志 | 关文件后仍正确输出 `48000Hz/1ch/...`，不再是「未建立」 |

真机麦克风链路仍需用户在 Air 上复测（本机无输入设备）。

## 用户要做的

装 `ObsidianDrop-1.3.14.dmg`，录一段话，点结束。应看到
`转写中 → 收尾中 → 归档中 → 灵感已归档`。

即使界面又出问题，文字也不会丢：菜单「打开运行日志」里会看到
「结果已落盘 → 待归档队列」；下次启动自动补写成笔记。
归档失败时会弹窗并给「复制文本」按钮。

  覆盖率日志已经就位，下次把日志发来即可判断。
