# ObsidianDrop 1.3.10（构建 14）— 转写不动的原因、进度释义、0 字诊断

## 一句话

录音能录，但转完没有文字（或者卡在「转写中」），而且**界面什么都不说**。
1.3.10 修了 3 个真 bug，给转写加了全链路进度释义，并在 0 字时直接告诉你卡在哪一环。

---

## 先说验证过程（结论是从实验来的，不是猜的）

这台 Mac mini 没有麦克风，所以我用音频文件走「同一套引擎」做了对照：

| 实验 | 输入 | 结果 |
|---|---|---|
| 文件路径（`--transcribe`） | 48 分钟会议录音，16kHz | **5578 字**（正常） |
| 文件路径 | 同一段前 60 秒，16kHz | **6 字** |
| 文件路径 | 同一段前 60 秒，48kHz Float32 | **10 字** |
| 文件路径 | 13 秒真实语音，48kHz Float32 | **184 字**（完整） |
| **流式路径**（`--transcribe-stream`，录音用的那条） | 13 秒真实语音，48kHz | **184 字**（与上面一致） |

**结论：48kHz / 硬件格式 / 流式投喂都没有问题。** 中间那两行「6 字 / 10 字」是我一开始的误判——
那段前 60 秒本身就是静音段，换成真正有人说话的音频后两种格式都出字正常。
（这一步排掉了一个本来打算修的「格式 bug」，也说明只看单点现象容易走错方向。）

转写引擎没问题 → 那「录音之后转写不成功」只能在**采集端**或**结束时的状态机**上。

## 找到并修掉的 3 个真 bug

### 1. 引擎没建好就点结束 → 静默 return，面板永远停在「准备中」

```swift
// 1.3.9
func stop() {
    ...
    guard let runner else { return }   // ← 什么都不说，什么都不发
    ...
}
```

首次使用时模型要下几分钟，用户看面板没动静就点「结束」，此时 `runner` 还是 nil：
`return` 之后没有任何回调，`memoState` 停在 `.preparing`，界面永远不动。
用户看到的就是「录音之后转写不成功」。

**1.3.10**：给出明确结局——弹窗说明「引擎还没准备好，等显示『录音中』再说话」，面板复位。

### 2. 送入音频的秒数按「源格式」累加，48kHz 录音被算成 3 倍时长

```swift
// 1.3.9
mutateDiag { $0.frames += AVAudioFramePosition(buf.frameLength) }   // 源是 48kHz
...
let audioSeconds = Double(readDiag().frames) / format.sampleRate    // format 是 16kHz
```

录音走的是麦克风硬件格式（常见 48kHz），除数却是分析器格式（16kHz）：
**10 秒录音被算成 30 秒**。这个数直接决定收尾超时上限
（`finalize = clamp(音频秒数/30, 10s, 180s)`），于是短录音也要白等十几秒；
反过来长音频也不会按真实长度放宽上限。

**1.3.10**：累加时按 `format.sampleRate / srcRate` 折算成分析器帧数，秒数恢复真实值。

### 3. 转写结果为 0 字时只有一句「没听清」

`memoDone` 里原本是：

```swift
guard !trimmed.isEmpty else {
    dropView.flash("没听清", ok: false)   // 就这一下，没有原因、没有数据
    return
}
```

而 0 字至少有四种完全不同的成因：没收到音频 / 收到了但没声音 / 格式转换失败 /
语言不匹配。四种的处置方式互不相同，界面上却一模一样。

**1.3.10**：新增 `MemoOutcome`（录音时长、送入引擎秒数、音量峰值、是否格式失败、是否来自文件），
0 字时弹出**带原因判断**的对话框，并可一键复制完整诊断：

```
听到了声音，但没转出文字
录音 0:12，送入识别 0:12，音量峰值 63%。

收到了 0:12 音频、音量峰值 63%，但一个字都没识别出来。
常见原因是语言不匹配（当前语言包：中文）……
```

判断顺序与文案：

| 条件 | 结论 |
|---|---|
| 送入 < 0.5 秒 | 引擎几乎没收到音频 → 查输入设备是否真的打开 |
| 音量峰值 < 2% | 收到了音频但全程没声音 → 查输入音量 / 静音键 / 外接麦 |
| 格式转换失败过 | 程序问题（不是用户设置问题），让用户把诊断发回来 |
| 其它 | 有声音但没识别 → 大概率语言包与所说语言不匹配 |

## 另外两处稳定性改造

### 文件转写改用 `analyzeSequence(from:)`

原来是自己 `读一块 → yield 一块 → 最后 finish()`。读文件几乎是瞬间的
（1 小时音频十几秒灌完），识别却要几十秒，中间的 buffer 全堆在 `AsyncStream` 里；
`continuation.finish()` 一关流，没消费完的部分就没了。

`analyzeSequence(from: AVAudioFile)` 是「处理完整个序列才返回」，本身带背压，从根上避免积压。
实测两条路结果一致（184 字 / 5578 字），但新路径不再依赖喂入与消费的运气。

### 录音 3 秒没声音就提醒一次

`memoLevel` 里判断：录音满 3 秒、峰值始终 ≤ 2%，面板闪一次
「没听到声音，检查输入设备」。这比转写完再猜原因有用得多。

## 所有转写现在都有进度释义

新增 `TranscribeProgress`（stage + 主行 + 副行 + 百分比 + 已处理/总时长 + 字数），
四个入口共用：现场录音、转写音频文件、转写剪贴板、命令行。

### 界面（面板标题就是进度）

```
准备中…          ← 查语言包 / 查模型 / 下载模型（每一步都有一句具体说明）
识别中 3:50 / 48:13（7%）   ← 主行
已出 52 字 · 剩余音频 44 分 23 秒   ← 副行
收尾中 0:05       ← 系统在消化最后一点音频，附带已等时长
```

- 录音中：`已识别 128 字 · 可以继续说`
- 百分比用 `SpeechAnalyzer.volatileRange.end` 实时读取，不是估算

### 命令行

```
· 准备语音转写…
· 准备识别 48 分 14 秒 的音频…
· 识别中 3:50 / 48:13（7%） · 已出 52 字 · 剩余音频 44 分 23 秒
· 收尾中 0:12 · 已出 5578 字 · 语音已录完，系统在消化最后一点音频
· 识别完成：5578 字 / 48 分 14 秒 音频
```

阶段变化立刻打印，其余每 2 秒一行，不会把终端刷满。

## 新增诊断命令

```bash
# 用「录音」那条代码路径转写一个音频文件，与 --transcribe 对照
/Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop --transcribe-stream <音频>
```

对照判读：

- **两边都出字** → 引擎没问题，问题在采集端（麦克风 / 权限 / 音量），看弹窗里的诊断；
- **只有 --transcribe 出字** → 流式投喂有问题（本次已修，若再出现把两条命令的输出发我）。
