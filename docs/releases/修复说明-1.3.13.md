## 一、先读你发来的那份日志

```
[20:59:26.632] 录音开始：录音-20261104-205926.caf，run 1
[20:59:54.134] 录音结束：墙钟 27.5s，文件 27.4s，5264896 字节，写失败 0 次，峰值 100%
[20:59:54.454] 识别完成：用时 0.1s，已出 0 字

[20:59:55.895] 转写完成：音频 27s，产出 58 字

```

逐条读：

| 结论 | 依据 |
|---|---|
| 麦克风和采集没问题 | 27.4 秒音频、5.26 MB、写失败 0 次、**峰值 100%** |
| 音频格式正常 | 5.26 MB ÷ 27.4 s ≈ 192 KB/s = 48kHz / 16bit / 立体声 |
| 转写成功了 | 58 字（27 秒口述，正常量级） |
| 收尾没超时 | 1.4 秒，限 15 秒 |
| **断点在交付** | 后面应该出现的「本轮结束 / 归档完成」一条都没有 |

也就是说：**音频存下来了、文字也出来了，是「把结果交给界面并写进库」这一步没发生。**

还暴露了两个更根本的问题（这才是这次要改的）：

1. **日志里没有版本号、机型、系统**。这份日志到底是 1.3.11 还是 1.3.12 打出来的，
   从文件里看不出来——只能靠「有没有某一行」去反推。排查一开始就少了一半信息。
2. **「结果没交上去」这件事本身没有任何记录**。上一版 `memoDone` 先过闸门再写日志：

   ```swift
   // 1.3.12
   func memoDone(...) {
       guard accept(run: run) else { return }   // ← 这里一旦拦掉，日志一个字都没有
       DiagLog.write("本轮结束：…")
   ```

   于是「后台根本没交」和「交了但被闸门拦掉」两种完全不同的故障，日志长得一模一样。

### 3. 每一次「回调没送到」都写原因

```swift
// 1.3.13
let lag = Date().timeIntervalSince(queuedAt)
guard let self else { DiagLog.round(run, "丢弃 \(what)：录音会话已释放"); return }
guard let s = self.sink else { DiagLog.round(run, "丢弃 \(what)：界面回调对象已释放"); return }
if lag > 0.4 { DiagLog.round(run, "主线程排了 3.2s 才处理 \(what)（主线程可能被堵住）") }
```

闸门拒绝也有原因：

```
run 1 ｜ 丢弃进度：本轮已收尾（界面已回空闲）
run 1 ｜ 丢弃结果：轮次不符（当前 run 2）
```

### 4. 主线程心跳（判断「是不是主线程被堵」的唯一手段）

只要有一轮在跑，主线程每秒醒一次，每 5 秒写一行：

```
run 2 ｜ 心跳：状态 转写中｜阶段 收尾中：已出 181 字 · 已等 0:03｜静默 0.3s｜进程已运行 5.9s
```

**如果日志里有后台的「转写完成」，却没有对应时间的心跳**——那就是主线程被堵住了，
而不是后台没干活。这两种毛病的修法完全相反，以前只能靠猜。

### 5. 看门狗：真卡死也不让人干等

| 阈值 | 动作 |
|---|---|
| 静默 20 秒 | 日志警告一行（正常流程不会出现：录音时音量每秒十几次，识别/收尾每 0.3~0.4 秒一条） |
| 静默 30 秒 | 界面闪一句「还在处理，请稍等…」，让人知道程序没死 |
| 静默 150 秒 | 强制恢复界面为可操作状态，弹窗给「打开日志」按钮 |

阈值取 150 秒而不是 90 秒，是因为首次下载语音模型前的那次检查最长可能安静 80 秒，
不能把正常等待误杀。

**关键：恢复界面不等于丢弃结果。** 闸门拆成了两个：

```swift
enum MemoGate {
    // 进度：轮次要对，且本轮未收尾
    static func acceptsProgress(run:current:stateIsIdle:) -> Bool
    // 结果：只比轮次——看门狗恢复过界面，后台那一轮的正文仍要收
    static func acceptsDone(run:current:) -> Bool
}
```

后台之后真出了结果，照常写笔记（界面会闪「灵感已归档」），日志里记
「结果迟到送达（看门狗已恢复过界面），照常归档，内容不丢」。

### 6. 下载语音模型时也报进度

首次使用要下几百 MB，原来界面上只有一句静态文案，几分钟不动；顺带也会被看门狗当成卡死。
现在每 0.3 秒报一次「正在下载「中文」语音模型…已等 1:20」，既让人安心，也告诉看门狗这一轮还活着。

### 7. 日志入口放进菜单

- 「打开运行日志」——直接打开 `~/Library/Logs/ObsidianDrop.log`
- 「复制日志路径」——复制路径，方便粘到聊天里
- 日志上限 200 KB → **512 KB**（一版日志的字段多了三倍）

## 五、附带修复的日志缺陷

- 「进程已运行」永远显示 0.0s：`static let = Date()` 是懒加载，首次访问才开始计时。改为在写启动头时重置计时起点。
- 「进度 ｜准备识别…」空标题：识别刚启动时的进度对象只有 `headline`、`stageTitle` 为空，日志里会写出一个空标题。现在两者取其一。
- 源码直跑时版本号显示 `0.0.0(0)`：改为 `源码直跑(-)`，一眼能分辨是不是走了 app 包。
