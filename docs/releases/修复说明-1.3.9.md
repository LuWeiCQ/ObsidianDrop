# ObsidianDrop 1.3.9（构建 13）— 修「有麦克风的电脑被判定没有麦克风」

## 一句话

在 MacBook Air 上点「灵感」录音，弹出「麦克风不可用：未检测到音频输入设备。**Mac mini 没有内置麦克风**，请接入 USB 麦克风后重试」——机器明明有内置麦克风，文案却在说另一台机器。

1.3.9 修掉了三件事：**设备探测不可靠**、**权限顺序错**、**文案写死机型**。

---

## 为什么会这样

### 根因 A（P0）：判断「有没有麦克风」只走了一条不可靠的路

```swift
// 1.3.8 及以前
let session = AVCaptureDevice.DiscoverySession(
    deviceTypes: [],          // ← 空数组被当成「不匹配任何类型」
    mediaType: .audio,
    position: .unspecified)
return !session.devices.isEmpty
```

`deviceTypes` 传空数组**不是**「不限类型」的可靠写法。按 Apple 的语义它是「候选类型集合」，
给空集合就匹配不到任何类型，返回空列表；而某些系统版本上它又恰好返回全部设备。
也就是说这个返回值是**不确定的**：

- Mac mini（真没麦克风）→ 返回空 → 判「没设备」，碰巧结论正确；
- MacBook Air（有内置麦克风）→ 也返回空 → 判「没设备」，**结论就错了**。

之前「这台 Mac mini 没有麦克风只能用文件转写」的结论，正是被这条 API 误导出来的。

### 根因 B（P1）：先探设备、后要权限

原来的顺序是「探测设备 → 请求麦克风权限」。首次运行时 TCC 还没决定，
部分系统版本在未授权状态下不返回输入设备列表——于是**第一次点录音必然失败**，
而且报的是「没有设备」，不是「没有权限」，用户会去查一个本来没坏的东西。
Air 是新装的机器，正好踩这个顺序。

### 根因 C（P1）：错误文案写死了机型

```swift
static let noMicAdvice = "未检测到音频输入设备。Mac mini 没有内置麦克风，……"
```

这段话在任何机器上都会原样弹出来。用户看到自己的 Air 被说成 Mac mini，
第一反应是「装错包了」，实际是探测失败。文案里还缺实测数据，远程没法定位。

## 1.3.9 改了什么

### 1. 五路探测，任一路有结果就算有设备

| 路 | 手段 | 说明 |
|---|---|---|
| ① | `DiscoverySession(deviceTypes: [.microphone])` | 明确的类型（macOS 14+；更早用内置麦克风 + 外接） |
| ② | `AVCaptureDevice.default(for: .audio)` | 系统默认输入，纯属性查询 |
| ③ | `AVCaptureDevice.devices(for: .audio)` | 旧接口兜底，专治 ① 返回空的历史 bug |
| ④ | **CoreAudio** `kAudioHardwarePropertyDevices` + 输入流配置 | 最底层，AVFoundation 出错时它仍然准；能看出是「真没设备」还是「上层没看到设备」 |
| ⑤ | `AVAudioEngine.inputNode.inputFormat` | 硬件真相：没设备是 `0 Hz / 0 ch`，有设备是硬件原生采样率 |

只有四路（①~④）全空、且引擎格式为 0 时才认定没有设备。
判定逻辑本身也必须在「有麦克风的机器」上正确——这一点现在有自检兜着（见下）。

### 2. 顺序修正：权限未决时先要权限，再复探

```
探测 → 不可用且权限「未决定」？→ 请求权限 → 复探 → 仍不可用才报错
                   ↘ 权限「已拒绝」→ 直接报权限错误（引导去设置）
```

这样首次运行不会再被误报成「没设备」，而是正常弹权限框；真被拒了就明确说权限。

### 3. 文案改成动态的，带实测结果

现在报错长这样（内容随实测变化）：

```
这台电脑没有可用的音频输入设备，所以无法录音。
实测：AVFoundation 设备：无；CoreAudio 设备：无；默认输入：无；输入格式：0 Hz / 0 ch；麦克风授权：未决定
可以按顺序排查：
1) 「系统设置 → 声音 → 输入」里是否选中了一个设备，输入电平条有没有跳动；
2) 外接麦克风 / 耳机是否插好；机身或键盘上的静音键是否把输入关了；
3) 如果只有「连续互通麦克风」，先在「音频 MIDI 设置」里确认它在线；
4) 在终端跑一次 ObsidianDrop --audio-check，把输出发回来能定位到具体哪一环。
...
```

「Mac mini」字样已彻底移除，并有断言 `无设备文案不写死机型` 防回归。

### 4. 新增诊断命令 `--audio-check`

```bash
/Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop --audio-check
/Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop --audio-check --json
```

只读探测：不请求权限、不启动采集、不录音。退出码 `0` = 有可用输入设备，`1` = 没有。
输出包含机型、系统版本、两层设备列表、默认输入、引擎输入格式、授权状态与结论。

读法只有一条：

- **CoreAudio 有设备、AVFoundation 为空** → 上层发现失败（本版已用多路探测绕开）；
- **两层都为空** → 系统层面确实没有输入设备，去「声音 → 输入」查；
- **设备有、授权「已拒绝」** → 权限问题，去隐私设置勾选后重开程序。

### 5. 错误弹窗加「复制诊断信息」

`micUnavailable` 的弹窗多一个按钮，点一下就把上面那份完整诊断拷进剪贴板。
远程排查不用再靠口述。

## 在 MacBook Air 上怎么验

1. **先把 dmg 里的 ObsidianDrop 拖进「应用程序」再运行。**
   直接从 dmg 窗口双击运行，每次挂载路径都不同，系统会当成另一个新程序，
   麦克风 / 截屏授权会反复失效——这一点已写进 dmg 内的《安装说明.txt》。
2. 首次点「灵感」→ 系统会弹麦克风授权（1.3.9 的顺序修正保证了这一步会正常出现）。
3. 允许后应当直接进入「录音中」。
4. 若仍报错，弹窗里点「复制诊断信息」，或跑：

   ```bash
   /Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop --audio-check
   ```

   把输出发回来即可定位。

新增的 7 项自检针对本次缺陷：

```
PASS  音频探测可执行
PASS  usable 与各路结果自洽
PASS  无设备文案不写死机型          ← 根因 C 防回归
PASS  无设备文案带实测结果
PASS  无设备文案指向诊断命令
PASS  诊断报告含机型与结论
PASS  诊断报告列出两层设备来源      ← 根因 A 防回归
```

本机（Mac mini，确实没有输入设备）实测输出：

```
ObsidianDrop 音频诊断
机型：Mac18,5
系统：版本27.0.1（版号26A434）
AVFoundation 设备：无
CoreAudio 设备：无
默认输入：无
引擎输入格式：未探测（麦克风未授权）
麦克风授权：未决定
结论：没有可用输入设备
exit=1
```

这台机器上「两层都为空」是对的；要验证「有麦克风时判对」，需在没有麦克风的机器之外
再跑一次 `--audio-check`，预期 `结论：有可用输入设备`、`exit=0`。

## 还剩什么没验证

- **没有第二台带麦克风的 Mac 可做端到端实测**。本次修复的判定逻辑用「多路冗余」把
  单点失效的可能性压掉，并在自检里锁住了「文案不写死机型」「两层来源都在」两条，
  但「Air 上点录音真的能录到声音」这一步需要你在 Air 上确认。
- 如果 Air 上 `--audio-check` 显示两层都有设备、授权也正常，却仍录不到，
  那问题就不在这条链路上（可能是设备被别的程序独占，会报「转写引擎启动失败」）。
  届时把诊断输出发我，再往下查。
