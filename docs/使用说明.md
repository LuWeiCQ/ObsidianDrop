# ObsidianDrop 使用说明

> 一个常驻桌面的投放窗口。把文件拖进去，自动归档到 Obsidian 库，并生成一条可检索的笔记。
> 位置：`~/Applications/ObsidianDrop.app`　｜　源码：仓库根目录（`./build.sh` 编译安装）

---

## 一、怎么用

1. 屏幕上有一个约 160×176 的圆角小窗（默认在右下角，可随意拖动，位置会被记住）。
2. 从访达 / 微信 / 浏览器把文件**拖到这个小窗上**（框内任意位置都行，不必对准边框），边框变蓝、标题变成「松手即归档」时松手。
3. 标题栏闪一下「已归档 N 个」，完事。

支持一次拖多个文件，也支持拖整个文件夹。

底部两个按钮：**截屏**（先收窗再拍，见第二节）和 **灵感**（录音自动转文字，见第三节）。

---

## 二、截屏

点小窗底部的 **`⛶ 截屏`**：

1. 窗口立刻收起（不会把自己拍进图里），

2. 屏幕变暗进入框选状态：按住拖出区域；按 `空格` 可拖动整块选区；按 `Esc` 取消（图中断，窗口自动回来，什么都不生成），

3. 松手后窗口自动回来，标题闪「截图已归档」，图片和笔记按当前目标落库：

```
附件/2026-11/2026-11-03 屏幕截图 14-51-14.png
00-收件箱/2026-11-03 屏幕截图 14-51-14.md
```

想截整屏 / 截某个窗口 / 只要剪贴板，走**右键菜单 → 截图**：

| 菜单项 | 效果 |
|---|---|
| 区域截图并归档 | 等于点按钮，拖选一块存到库里 |
| 整屏截图并归档 | 直接拍主显示器，不框选 |
| 窗口截图并归档 | 鼠标变成相机，点哪个窗口拍哪个（不带阴影） |
| 区域截图到剪贴板 | 拖选后只进剪贴板，方便直接粘到微信/文档 |

> **第一次用会失败**，因为 macOS 要求「屏幕录制」权限，按提示点「打开设置」勾上 ObsidianDrop 即可，然后**退出重开**这个程序。每次重新 `./build.sh` 编译后签名会变，个别情况下系统会要求重新授权一次。

## 三、灵光一现（录音转文字）

点小窗底部的 **`💡 灵感`**，立刻开始录音：

1. 图标变成红色麦克风，标题显示「录音中 0:07」，会随你说话的音量轻微呼吸
2. 副标题提示「说完点「结束」，再转成文字」——**录音这一段只负责把声音存下来**，
   界面上不出实时文字；能呼吸、有计时，就说明确实在收音
3. 说完再点一下（按钮已变成 **`■ 结束`**），程序先把音频存成一个本地文件，
   再把文件交给转写引擎：图标位置变成**进度环 + 中间的大号百分比**，
   标题写「转写中」，副标题写「已出 N 字 · 剩 1:20」，完成后闪「灵感已归档」

> 为什么先存文件再转写：这样「录音」和「识别」互不牵连。识别引擎没装好、
> 模型还在下载、甚至语音识别权限没给，录音都不会丢——音频已经在你本机上了。

### 转写过程中的进度是什么意思

进度用**图标位置上的圆环**表示，环中间的百分比是实时的：

| 面板显示 | 在做什么 | 正常要多久 |
|---|---|---|
| 准备中 + 转圈环、副标题「检查语音模型是否已安装…」 | 查语言包 / 查模型 | 1 秒 |
| 准备中 + 转圈环、副标题「下载…语音模型…」 | 下几百 MB 的模型（首次） | 几分钟，最长等 10 分钟 |
| 转写中 + **环 + 百分比**、副标题「已出 63 字 · 剩 1:20」 | 正在识别 | 约 80 倍实时 |
| 收尾中 + 转圈环、副标题「已出 120 字 · 已等 0:05」 | 音频已送完，系统在消化尾巴 | 录音 1～3 秒；长文件十几秒 |
| 归档中 + 转圈环、副标题「已识别 312 字」 | 把笔记和附件写进库 | 几十毫秒～几秒（库在 iCloud 上偏慢） |

百分比是实时读系统「已处理到音频第几秒」算出来的，不是估算。
**收尾阶段故意不显示百分比**（那会儿音频已经 100% 送完，给个 100% 会让人以为卡住），
改用转圈环 + 已等时长。

**录音 3 秒还没有任何声音**时，面板会闪一次「没听到声音，检查输入设备」——
这时候别继续录，先看输入设备。

生成的笔记（当前目标是收件箱时）：

```
00-收件箱/2026-11-03 灵感 15-48-26.md
```

内容长这样：

~~~markdown
---
类型: 灵感速记
创建时间: 2026-11-03 15:48
时长: 1:13
目标: 00-收件箱
转写: 端上本机（DictationTranscriber / 中文）
tags:
  - 灵感
  - 收件箱
---

# 灵感 2026-11-03 15:48

这是第一条灵感：MES 上线前要把压力测试脚本准备好。

第二条：路演材料周五定稿。

> [!note] 录制信息
> - 时长：1:13
> - 转写：Mac 本机完成，未上传云端
~~~

几个设定：

| 项目 | 说明 |
|---|---|
| 语音模型 | macOS 26 起的端上模型（`DictationTranscriber`），**首次使用自动下载**，之后秒开 |
| 识别语言 | 默认中文；改英文：`defaults write com.lw.obsidiandrop memoLocale en-US` |
| 时长上限 | **录音 5 分钟**，到点自动结束并转写（文件转写不限时长，见下） |
| 数据去向 | 全程本机，不上传。录音会**先落盘**到 `~/Library/Application Support/ObsidianDrop/recordings/`，转写成功后自动删除；没转出字时保留，方便重试或在访达里播放确认 |
| 取消 | 准备阶段点「取消」；录音中点「结束」即转写，没有「丢弃」这一档 |
| 记录位置 | 跟着当前投递目标走，选项目就写进项目目录 |

> **第一次点会弹两次权限**：「麦克风」和「语音识别」，都点允许。拒了之后再点会提示去系统设置里打开。

**关于时长**（实测数据，Mac mini / macOS 27）：

| 场景 | 上限 | 实际耗时 |
|---|---|---|
| 现场录音 | 5 分钟硬上限（`Memo.maxSeconds = 300`，改源码可调） | 边录边转，结束时几秒出字 |
| 转写音频文件 | **无上限** | 10 分钟音频 ≈ 8 秒；1 小时 ≈ 46 秒（约 80 倍实时） |

底层用的是 macOS 26 的 `SpeechAnalyzer`，**没有** `SFSpeechRecognizer` 那种「单次 1 分钟」的限制。长音频的收尾时间会按音频长度自动放宽（下限 10 秒、上限 3 分钟），避免把尾巴丢掉——这一点在 1.3.3 修过（旧版固定 10 秒，1 小时音频会丢尾部）。

### 没有麦克风怎么办

先分清是「这台机器真没有」还是「程序没看到」——1.3.9 起有专门的诊断命令，只读、不录音、不弹权限框：

```bash
/Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop --audio-check
```

- **AVFoundation 设备、CoreAudio 设备都为空** → 系统层面确实没有输入设备。
  Mac mini 是这样（机型本身不带麦），接一个 USB 麦克风再点「灵感」即可；
- **CoreAudio 有设备、AVFoundation 为空** → 上层发现失败，1.3.9 的多路探测已经能绕过去；
- **设备有、授权「已拒绝」** → 权限问题，去「系统设置 → 隐私与安全性 → 麦克风」勾上再重开程序。

只想把**已有的录音**变成文字 → 用右键菜单里的 **「转写音频文件…」**，选一个音频文件
（m4a / wav / mp3 都行），转完同样生成一条「灵感」笔记。这条路不需要麦克风。

**如果文件在面板里是灰的、点不动**（外部拷来的文件常见）：

在 Finder 里选中那个文件按 ⌘C 复制，再点菜单 **「转写剪贴板里的音频」**——完全不经过面板，直接开转。

根因见下面排错段的「文件在面板里是灰的」。

命令行等价写法：

```bash
"$HOME/Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop" --transcribe ~/Downloads/录音.m4a
```

## 四、投放后发生了什么

**目标 = `00-收件箱`（默认）**

```
附件/2026-11/2026-11-03 会议通知.pdf      ← 文件本体，会同步到手机
00-收件箱/2026-11-03 会议通知.md          ← 笔记，会同步到手机
```

笔记内容：

```markdown
---
类型: 文件归档
文件: 附件/2026-11/2026-11-03 会议通知.pdf
归档时间: 2026-11-03 14:40
来源目录: ~/Downloads
目标: 00-收件箱
tags:
  - 收件箱
---

# 会议通知

![[附件/2026-11/2026-11-03 会议通知.pdf]]

> [!note] 投递记录
> - 原始位置：`~/Downloads/会议通知.pdf`
> - 大小：248 KB
> - 存放位置：`附件/`，会随库同步到手机
> - 由 ObsidianDrop 于 2026-11-03 14:40 投递到「00-收件箱」

## 说明
```

`## 说明` 留空，供你补一句用途。之后在 Obsidian 里把这条笔记拖到对应项目即可。

**目标 = 某个项目（如 `凯翼汽车`）**

```
10-项目/凯翼汽车/文档/2026-11-03 现场照片.png   ← 文件进「文档/」，会同步到手机
10-项目/凯翼汽车/2026-11-03 现场照片.md         ← 笔记放在项目根目录
```

两种目标现在都能在手机上看：项目文件进 `文档/`，随手收的进 `附件/`（2026-11-03 晚起附件也发布到 iCloud 镜像）。
`附件/` 有个容量兜底——总量超过 1GB 时发布脚本会自动跳过附件目录、只发笔记，避免撑爆 5GB 免费配额。

## 七、命令行用法

编译好的二进制在 app 包内，可以脱离界面直接投放，适合接 Automator、快捷指令或脚本：

```bash
BIN="$HOME/Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop"

# 投放单个文件到收件箱
"$BIN" --file ~/Downloads/报告.pdf

# 批量投放，指定项目
"$BIN" --file ~/a.pdf ~/b.png --target "10-项目/凯翼汽车"

# 整屏截图并归档（不弹框选，适合定时任务）
"$BIN" --shot full
"$BIN" --shot area --target "10-项目/凯翼汽车"

# 区域截图只进剪贴板（不入库）：成功与取消都返回 0
"$BIN" --shot clipboard

# 把一段音频转成文字（先切成 wav/m4a 都行）
"$BIN" --transcribe ~/Downloads/录音.m4a

# 转写并直接写成灵感笔记
"$BIN" --transcribe ~/Downloads/录音.m4a --target "10-项目/凯翼汽车"

# 结果另存一份（脚本里读）
"$BIN" --transcribe ~/Downloads/录音.m4a --out /tmp/文字.txt

# 开机启动开关
"$BIN" --login on
"$BIN" --login off

# 走完整界面链路跑一遍（转写 → 归档 → 界面复位），跑完自己退出
# 退出码：0 已归档并复位 / 1 中途失败 / 2 超时或看门狗恢复
"$BIN" --ui-memo ~/Downloads/录音.m4a --target "00-收件箱" --vault /tmp/测试库
```

输出是两行一组，便于脚本解析：

```
笔记: 00-收件箱/2026-11-03 报告.md
文件: 附件/2026-11/2026-11-03 报告.pdf
```

## 八、重新编译

改了源码后：

```bash
cd ~/WorkBuddy/个人/work/obsidian-drop
./build.sh          # 编译并覆盖安装到 ~/Applications
```

只依赖 Xcode 命令行工具（`swiftc`），不需要 Xcode、不需要 Homebrew、不需要 OpenSSL 之类的东西。

**只编 arm64（Apple Silicon）。** 不做 Intel 适配：目标机器都是 M 系列，单架构产物更小。

## 九、打包成 dmg

```bash
cd ~/WorkBuddy/个人/work/obsidian-drop
./package-dmg.sh              # 先编译再打包
./package-dmg.sh --no-build   # 用现有产物直接打包
```

产物：`dist/ObsidianDrop-<版本>.dmg`（当前 1.3.15，约 322KB）。里面三样东西：

```
ObsidianDrop.app
Applications -> /Applications    ← 拖过去即安装
安装说明.txt                      ← 首次打开、权限、开机自启都写在里面
```

脚本自带自检：挂载 dmg → 验证可执行文件 → 验证 Applications 快捷方式 → `codesign -v` → 卸载，最后打印 SHA256。

版本号在 `build.sh` 的 Info.plist 里（`CFBundleShortVersionString` / `CFBundleVersion`），改版本改这两行。

> 应用是 ad-hoc 签名（没有开发者证书、没有公证）。别人从微信/网盘拿到 dmg 会被 Gatekeeper 拦：右键 → 打开 → 再点「打开」，或 `xattr -dr com.apple.quarantine /Applications/ObsidianDrop.app`。
脚本会：写 `Info.plist` → `swiftc -O` 编译 → ad-hoc 签名 → 装到 `~/Applications` → 去 quarantine 标记。

## 十、排错

**拖进去报「归档失败：Operation not permitted」**
→ macOS 隐私保护。系统设置 → 隐私与安全性 → 完全磁盘访问权限 → 加入 `ObsidianDrop.app`。

**点截屏没反应 / 报「截图失败」**
→ 没给「屏幕录制」权限。系统设置 → 隐私与安全性 → 屏幕与系统录音 → 勾上 ObsidianDrop → **退出重开程序**。
→ 重新编译（`./build.sh`）后签名会变，系统可能要求再授权一次。

**截屏把小组件自己拍进去了**
→ 旧版本没有收起逻辑，重新编译安装即可；现在点击后固定等 0.3 秒待窗口消失再拍。

**点「灵感」报「录音失败：没有麦克风权限」/「没有语音识别权限」**
→ 系统设置 → 隐私与安全性 → 对应那一栏勾上 ObsidianDrop，然后**退出重开程序**。
→ 弹窗里点「打开设置」可直接跳过去，改完必须重开程序才生效（TCC 是进程级缓存）。

**录音有红点、有波形，但一直不出字**
→ 1.3.11 起录音**不再显示实时文字**（录音只存文件，转写等录完再做），
   所以「录音中」看不到字是正常的，看的是：图标随音量呼吸、计时在走。
→ 结束之后如果没出字，看弹窗给的原因（会给四种判断之一）：
   · **「引擎几乎没收到音频」** → 麦克风没被系统真正打开，查「系统设置 → 声音 → 输入」
   · **「全程几乎没有声音，峰值 N%」** → 输入音量太小 / 静音键 / 外接麦没插好
   · **「格式转换一路有失败」** → 程序问题，不是你的设置问题，把诊断发我
   · **「有声音但没识别出文字」** → 多半是语言包不匹配，见下一条
→ 识别语言与你说的话不匹配：`defaults write com.lw.obsidiandrop memoLocale en-US`，再重开程序。
→ 弹窗里若出现「在访达中显示录音」，说明**这次录音已经存下来了**：点它可以播放确认
   里面到底有没有声音；也可以右键菜单「转写音频文件…」选这个文件重新转一次。
→ 想进一步定位，跑一次按钮链路自检（把音频按录音的方式写文件再转写）：
   `/Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop --record-test <音频>`
   输出里「写入 … 秒 · 回读 … 秒 · 转写 N 字」三项都对，说明程序这一侧没问题，
   问题就在采集端（麦克风/权限/音量）。

**转写完了提示「没识别出文字」，还弹了个框**
→ 这是 1.3.10 新增的诊断。框里写明了「录音多久、送入识别多久、音量峰值多少」，
   并按最可能的原因给出结论；点「复制诊断信息」可以把整份内容发给我。
→ 日志里也会留一行：`转写为空 —— 录音 0:12，送入 0:12，峰值 63%，格式失败 false`

**转写完提示「没听清」**
→ 太短（< 0.6 秒）或全程静音都不会生成笔记，避免留下一堆空文件。

**点「灵感」闪退（程序直接消失）**
→ 1.3.2 已修。这是老问题：装麦克风 tap 时传了系统回退出来的**假格式**，
底层 `AVAudioEngineGraph` 抛 NSException（Swift 捕不住）→ SIGABRT。
现在改成先独立确认设备存在、用硬件真实格式、并让引擎走原生格式，不会再崩。
→ 若仍遇到，看 `~/Library/Logs/DiagnosticReports/ObsidianDrop-*.ips` 里的 `lastExceptionBacktrace` 发我。

**点「灵感」提示「未检测到音频输入设备」**
→ **先跑一次诊断**，别急着找麦克风：
`/Applications/ObsidianDrop.app/Contents/MacOS/ObsidianDrop --audio-check`
→ 1.3.8 及以前这条判断只用了一条不可靠的 API（`DiscoverySession(deviceTypes: [])`，空数组
并不等于「不限类型」），**在本来有内置麦克风的 MacBook Air 上也会返回空**，于是被误判成
「没有设备」，弹出来的还是写着「Mac mini 没有内置麦克风」的旧文案。1.3.9 已改为五路探测 +
先要权限再复探，并移除了写死机型的文案。
→ 诊断里两层设备都为空 = 确实没有输入设备（Mac mini 属于这种），接 USB 麦克风，
或用菜单「转写音频文件…」处理已有录音。

**点「结束」后一直卡在「转写中…」不结束**
→ 早期版本里 `finalizeAndFinishThroughEndOfInput()` 在某些内核状态下会永久挂起，导致面板永远停在「转写中」。**1.3.1 已加超时兜底**：无论系统转写内核是否卡死，`finish()` 都会在限时后强制返回，面板随之退出「转写中」（可能尾部少几个字，但不会无限转圈）。
→ 这个限时**不是固定 15 秒**：1.3.3 起按音频长度算——录音（≤5 分钟）约 10～15 秒，转写 1 小时的文件最长可等到 3 分钟收尾。等得久不等于卡死，长文件耐心些。
→ **1.3.12 起，界面永远停住这件事本身已经修了**：「完成」和「进度」是两条路径投递到主线程的，最后那条进度常晚于完成到达，把面板画回「收尾中」且再无人更新——现在每条回调都带轮次编号，本轮结束之后的一律丢弃。
→ **1.3.13 起再加一层兜底**：只要有一轮在跑，主线程每秒打一次心跳；静默 20 秒记警告、30 秒闪「还在处理」、**150 秒强制把界面恢复成可操作状态**。
→ **1.3.14 起，文字不会再因为界面出问题而丢**：转写完先原子落盘进「待归档队列」，再交付界面。交付失败（会话释放、轮次被顶掉、进程退出都算）时，由看门狗或下次启动补写进笔记，录音也是写成功之后才删。
→ 还出现长时间停住，直接看落盘日志 `~/Library/Logs/ObsidianDrop.log`，或菜单「打开运行日志」。1.3.14 的日志是**逐阶段 + 带轮次 + 带落盘编号**的，形如：

```
===== 启动 ｜ 版本 1.3.14(18) ｜ MacBookAir10,1 ｜ Version 27.0 ｜ PID 59702 ｜ 库 … =====
run 2 ｜ 本轮开始：现场录音 → 目标「00-收件箱」，语言 zh-CN
run 2 ｜ 设备探测：AVCapture 1 个 / CoreAudio 1 个 / 默认输入 MacBook Air 麦克风 / 权限 已授权 / 可用 是
run 2 ｜ 状态 准备中 → 录音中｜-
run 2 ｜ 录音结束：墙钟 27.5s，文件 27.4s，5264896 字节，格式 48000Hz/2ch/int16，帧 1317120，写失败 0 次，峰值 100%
结果覆盖：3 段定稿（partial 291 条），覆盖 130.1s / 180.0s（72%），最长空白 38.9s
run 2 ｜ 转写返回：1.6s，音频 27.4s → 58 字
run 2 ｜ 结果已落盘：F0257…（58 字）→ 待归档队列
run 2 ｜ 交付结果到主线程（done）
run 2 ｜ 收到结果：58 字 …｜界面 转写中，当前 run 2
run 2 ｜ 归档完成：0.02s → 00-收件箱/2026-11-04 灵感 20-59.md
```

最后一行停在哪，卡的就是哪一步；整份发我即可，不用再描述现象。判断表：

| 日志停在 | 含义 |
|---|---|
| 有「转写完成」但没有「收到结果」 | 结果没送到界面；若同时**心跳也断了**，是主线程被堵住 |
| 有「结果已落盘」但没有「归档完成」 | 界面没接住，但文字已在队列里：看门狗 150 秒或下次启动会自动补写 |
| 有「补归档完成」 | 队列兜底生效，笔记已经写进去了，内容没丢 |
| 有「归档失败」 | 库路径/权限有问题；文字和录音都保留着，修好库后重启即可补写 |
| 有「看门狗：N 秒无事件」 | 后台真的没进展，界面已自动恢复；紧跟着看有没有「补归档成功」 |
| 有「结果覆盖：…（xx%）」 | 文字盖住了多少音频。低于 50% 且音频超过 10 秒时，下一行会提示疑似丢字（安静说话也会有这种形状，只作线索） |

**wav 文件「识别不出来」/ 提示「没有识别到语音」**
→ 先看是不是**文件头长度不对**。很多录音笔、手机、边录边写的程序会把 wav 的 `data` 长度字段写成 `0`（中断、断电、导出前没回填），`AVAudioFile` 会严格按声明长度读 → 一帧都读不到 → 看起来就像「这个 wav 不认识」。
→ **1.3.4 起自动修**：读之前按文件实际大小把 `RIFF` / `data` 两处长度改回来（落一份临时副本，不动原文件），日志里会有 `修正 wav 头：data 声明 0 → N 字节`。正常文件不会触发修正。
→ 若仍失败，会给出明确提示「读不出 xxx 里的音频数据」而不是含糊的「没有识别到语音」。这时用「音乐」或 QuickTime 打开确认能播放，再另存为 m4a 试一次。
→ 支持的格式实测覆盖：16k/22k/44.1k/48k、单声道/立体声/6 声道、16/24/32 位浮点 wav，以及 aiff、m4a、mp3；8kHz 电话录音、音量很小的录音也都能出字。

**文件在面板里是灰的、点不动（wav 尤其常见）**
→ 不是格式不支持，也不是程序过滤类型。是**文件自身的元数据被系统标成了「不可用」**：从 Windows / 手机 / 某些传输工具拷过来的文件，`com.apple.FinderInfo` 里常带着 `brok` 类型码（"broken"），Launch Services 据此把它在打开面板里置灰。
→ 判断方法：`xattr -px com.apple.FinderInfo 文件路径`，前 4 个字节是 `62 72 6F 6B` 就是它。
→ 最快的解法是**重建一份**（内容不变、文件名不变）：
```bash
f="你的文件.wav"; cp "$f" /tmp/rebuild.tmp && mv -f /tmp/rebuild.tmp "$f"
```
（2026-11-04 实测：同一个 37MB 会议录音，只有原文件灰、`cp` 出来的副本直接可选、转写正常）
→ 不想动文件的话，用菜单「转写剪贴板里的音频」：Finder 里 ⌘C 复制，直接转。1.3.5 起面板也不再按类型过滤文件，能选就选。

**转写一直停在「检查语音模型…」/ 报「语音转写服务没有响应」**
→ 这一步要连 Apple 的资产服务与系统语音服务。网络/代理不通、或「语音识别」权限没给时都会卡住。
→ 1.3.2 起每一步都有上限（查 locale 20s、查模型 60s、下载 10 分钟、建引擎 30s），超时会给明确报错而不是无限转圈。
→ 先确认「系统设置 → 隐私与安全性 → 语音识别」里勾上了 ObsidianDrop，然后退出重开程序。

**窗口不见了**
→ 点菜单栏托盘图标 → 显示；或「把窗口移到右下角」。

**库里没出现笔记**
→ 检查菜单里「投递目标」是否指到了某个你没在看的目录；命令行跑一次 `--file` 能看到实际写入路径。

**手机上看不到附件里的图**
→ 先确认 `~/Obsidian/logs/publish.log` 最近一轮是否「完成」，再确认 `Main-Mobile/附件/` 里有没有这个文件。
→ 若日志里有「附件已达 XXXMB，超过 1024MB 上限」，说明触发了容量兜底，删掉些大文件或调 `ATTACH_LIMIT_MB` 即可。

**重名文件怎么办**
→ 自动加 `-2`、`-3`，不覆盖。

## 十一、技术要点

- 纯 AppKit，`LSUIElement = true`（不进 Dock，只占菜单栏）
- 窗口 `level = .floating`，`collectionBehavior` 含 `canJoinAllSpaces`，切桌面跟着走
- 归档逻辑在 `Filer` 里，界面和命令行**共用同一份代码**，测试即生产
- 文件名会清掉 `[ ] | # ^ \ / : * ? " < >` —— 这些字符会破坏 Obsidian 的 wikilink
- 笔记用**全路径 wikilink**（`[[附件/2026-11/x.pdf]]`），同名文件不会串
- **整块面板都是投放区**：`DropView.hitTest` 直接返回自己，毛玻璃层、图标、文字、截屏按钮一律不参与命中。否则这些子视图会把拖放命中截断，只剩没被覆盖的最外圈边框能触发（2026-11-03 修）
- 截屏按钮因此不再自己接点击，改由 `DropView.mouseUp` 按坐标判定，避免按钮那块变成投放死区
- 截屏调系统 `/usr/sbin/screencapture`，不自己抓屏：虚拟屏、外接屏、HiDPI 都由系统处理，也不会漏掉其它 App 的窗口
- 截图前 `panel.orderOut` 只临时收起，**不改写**「面板可见」偏好，截完原样回来；截屏进程在后台线程跑，界面不卡
- 转写用 macOS 26 的 `SpeechAnalyzer` + `DictationTranscriber`（**端上**，音频不上传，也没有 SFSpeechRecognizer 那种 1 分钟限制）
- `SpeechRunner.finish()` 用「轮询 + 双超时」收尾：`continuation.finish()` → 限时 `finalizeAndFinishThroughEndOfInput()` → 限时等结果流。任一环节挂起都不会无限拖住面板（2026-11-03 / 1.3.1 修「一直卡在转写中」）。
  两个限时**按已喂入的音频时长动态计算**（`finalize = clamp(时长/30, 10s, 180s)`、`drain = clamp(时长/120, 5s, 30s)`）：实时录音积压少、10 秒足够；整段文件转写时灌入速度远快于分析速度，固定 10 秒会把长音频的尾巴丢掉（2026-11-04 / 1.3.3 修；实测 1 小时音频 46 秒转完，修前 21 秒即被强杀）
- **装麦克风 tap 必须先确认设备存在**：没有输入设备时 `inputNode.outputFormat` 会回退出一个 44100/2ch 的**假格式**，拿它去 `installTap` 底层会抛 NSException 直接闪退。要用 `inputFormat`（无设备时是 0/0）+ `installTap(format: nil)` 走硬件原生格式（2026-11-03 / 1.3.2 修）
- **判断「有没有麦克风」不能只用一条 API**：`AVCaptureDevice.DiscoverySession(deviceTypes: [], mediaType: .audio, ...)` 传空数组**不是**「不限类型」，按语义是「不匹配任何类型」，会返回空列表——在**有内置麦克风的 MacBook Air 上**也返回空，于是被判成「没有输入设备」。同理，**首次运行权限未决定时**部分系统版本也不返回设备列表，所以「先探设备、后要权限」的顺序必然让第一次点录音失败。1.3.9 改为五路探测（明确 deviceTypes / `default(for:)` / `devices(for:)` 兜底 / **CoreAudio** `/ 引擎 `inputFormat`）任一路有即算有，并在权限未决时先请求再复探（2026-11-04 / 1.3.9 修）。排查入口：`ObsidianDrop --audio-check`
- **统计「送进去多少音频」必须折算到分析器格式**：录音 buffer 是硬件格式（常见 48kHz），分析器格式是 `bestAvailableAudioFormat`（常见 16kHz）。直接累加源帧会让 10 秒录音算成 30 秒，而这个数决定收尾超时上限（`clamp(秒数/30, 10s, 180s)`）——短录音白等、长音频又不够等。正确写法：`frames += 帧数 * format.sampleRate / buf.format.sampleRate`（2026-11-04 / 1.3.10 修）
- **录音绝不要「边录边喂识别引擎」，先落盘再按文件转写**：边喂的成败取决于「喂入速度 vs 分析速度」的运气，更致命的是引擎要等语音模型装好才能建——首次使用时用户点「结束」可能根本没有引擎，而那时音频已经不在任何地方了（表现就是「录音之后转写不成功」）。改成录音只写文件、结束后走 `transcribeFile` 之后，两条路彻底解耦，失败也有原始音频可重试（2026-11-04 / 1.3.11 改）
- **`AVAudioFile(forWriting:settings:commonFormat:interleaved:)` 必须用第一块 buffer 自己的格式**：`write(from:)` 要求 buffer 格式与文件 `processingFormat` 严格一致，不一致抛的是 ObjC 异常，Swift 接不住 → SIGABRT。所以格式从数据来，不从设备查询来；录音 tap 改用 4096 帧一块
- **`close()` 里不能把采样率一起清掉**：关文件后还要用「帧数 / 采样率」算时长，清掉就会把 12 秒音频算成 0 秒，然后误判成「没有录到音频」（实测第一版就踩了，靠 `--record-test` 打出「写入 0.0 秒 / 2496036 字节」才暴露）
- **录音落盘目录要有回收**：成功即删、失败保留（给「在访达中显示录音」和重新转写用），启动时清掉 7 天前的残留，否则失败录音会无声堆在 `~/Library/Application Support/ObsidianDrop/recordings/`
- **小面板的进度要放在图标上，标题别塞百分比**：160pt 宽的标题写「识别中 3:12 / 12:00（27%）」必被截断；改成图标位置的圆环 + 中心大字百分比、标题只写「转写中」、副标题「已出 63 字 · 剩 1:20」。收尾阶段不给百分比（音频已 100% 送完，给 100% 会让人以为卡住），改转圈环 + 已等时长（2026-11-04 / 1.3.11 改）
- **排版不要靠猜**：`ObsidianDrop --render-preview <目录>` 把面板各状态离屏渲染成 PNG，改完直接看图；实测靠它发现过副标题被中间省略截成「已出 63 字 ·...频 1 分 20 秒」、以及准备阶段的说明整句不显示（当时只渲染了 `detail`，而准备阶段的话在 `headline` 里）
- **文件转写要用 `analyzeSequence(from: AVAudioFile)`，别自己「读一块 yield 一块」**：读文件是瞬间的（1 小时音频十几秒灌完），识别要几十秒，未消费的 buffer 堆在 `AsyncStream` 里；`continuation.finish()` 一关流，剩下的一起丢。`analyzeSequence` 是「处理完整序列才返回」，自带背压。实测两条路结果一致（184 字 / 5578 字），但新路径不依赖喂入与消费的运气（2026-11-04 / 1.3.10 改）
- **进度回调必须带「轮次」，并且本轮收尾后一律丢弃**：收尾阶段后台每 0.3 秒推一条，`memoDone` 又要写笔记（几百毫秒），最后那条进度常常晚于完成回调执行——把界面重新画成「收尾中」，之后再也没有事件更新，表现就是「一直卡在转写收尾中」。判据要两条同时成立：`run == 当前轮` 且 `状态 != idle`；只做其中一条都能被绕过（2026-11-04 / 1.3.12 修）
- **写库不能在主线程、更不能在重绘之前**：`Filer.memo()` 复制附件 + 落 md，库在 iCloud 上时要几秒。同步跑在主线程且发生在 `renderMemo(.idle)` 之前，会让窗口既失去响应又仍显示「收尾中」，和转写卡死在观感上无法区分。正确做法：先渲染一个独立状态（「归档中」），IO 丢后台，完成后回主线程闪结果（2026-11-04 / 1.3.12 改）
- **`analyzeSequence` 没有内建超时**：真机上语音服务异常时可能永不返回，界面就永远「识别中」。按音频长度给上限（`clamp(秒数/8, 90s, 20min)`），超时带着已出文字收工（2026-11-04 / 1.3.12 加）
- **日志要落成文件，不要让用户读系统日志**：`NSLog` 进的是统一日志，用户的 Mac 上取不出来，一句「卡住了」发过来只能猜。`~/Library/Logs/ObsidianDrop.log` 逐阶段记（录音时长/识别耗时/收尾耗时/字数/归档结果），超 512KB 自动重来（1.3.12 加 / 1.3.13 扩充）
- **日志必须带版本、且「丢弃」也要留原因**：1.3.12 的现场日志里既没有版本号，`memoDone` 的日志又写在闸门**之后**——于是「后台没交结果」和「交了但被闸门拦掉」两种故障的日志长得一模一样，只能靠反推。1.3.13 起：启动头写版本/机型/系统/库/PID，回调每次丢弃写原因（会话已释放 / 界面对象已释放 / 轮次不符 / 已收尾），投递延迟 > 0.4 秒也记一笔（2026-11-04 / 1.3.13 改）
- **判断「主线程被堵」只能靠心跳**：后台日志照常写（日志队列在别的线程），主线程被堵时界面不动、回调排不上队，但日志里**只有后台那几行**。所以每轮运行期间主线程每秒醒一次、每 5 秒写一行「心跳：状态/阶段/静默 N 秒」；心跳缺失 = 主线程被堵，心跳正常而静默变长 = 后台没进展，两者修法完全不同（2026-11-04 / 1.3.13 加）
- **看门狗恢复界面 ≠ 丢弃结果**：静默 150 秒强制把界面恢复成 idle，用户能继续操作；此时后台那一轮可能还活着，所以「结果」的判据只比轮次、**不要求状态非 idle**，迟到送达照样归档（进度则仍需 `状态 != idle`，否则会重绘回「收尾中」）。这两种判据必须分开写，合成一条就会二选一地出问题（2026-11-04 / 1.3.13 改）
- **`static let = Date()` 是懒加载**：`DiagLog.launchedAt` 写在 `uptime()` 里首次访问才初始化，于是日志里的「进程已运行」永远是 0.0s。改为在写启动头时显式重置起点（2026-11-04 / 1.3.13 修）
- **界面问题要能自动复现**：`--ui-memo <音频>` 走**完整界面代码路径**（与点菜单「转写音频文件…」同一条），跑完自动退出并给退出码（0 归档并复位 / 1 失败 / 2 超时或看门狗恢复）。配合 `OBSIDIANDROP_DROP_DONE=1`（模拟结果交不上去）与 `OBSIDIANDROP_DELAY_DONE=22`（结果延后到达）两个环境变量，可以在这台没有麦克风的机器上把「卡在收尾中」这一类问题完整复现并验完（2026-11-04 / 1.3.13 加）
- **转写空结果不能只闪一句「没听清」**：0 字至少有四种成因——没收到音频 / 收到但没声音 / 格式转换失败 / 语言不匹配，处置方式完全不同。必须采集 `MemoOutcome`（录音时长、送入秒数、音量峰值、是否格式失败）并分别给结论（2026-11-04 / 1.3.10 加）
- **`AnalyzerInput(buffer:)` 里是 Swift 运行时断言**：格式不合规直接 SIGTRAP，catch 都接不住。所以 macOS 27+ 用官方 `AnalyzerInputConverter`（抛可捕获错误），macOS 26 用自研转码 + 逐项格式闸，投喂前最后再核一次
- **`AVAudioFile.read` 读到文件末尾会抛 eofErr**（`NSOSStatusErrorDomain`, -39），那是「读完啦」不是错误；用 `framePosition < length` 判断并显式吞掉，否则整段转写会在最后一步中断
- **CLI 里不能 `sem.wait()` 堵主线程**：`main()` 跑在主 actor 上，普通 `Task {}` 会继承主 actor 隔离，主线程被占住就永远排不上队 → 死锁。必须 `Task.detached` + 边等边转主循环
- **文件在打开面板里置灰 ≠ 格式不支持**：从外部拷来的文件常在 `com.apple.FinderInfo` 里带 `brok` 类型码，Launch Services 判定「不可用」后，NSOpenPanel 里就是灰的、点不动，连 `allowedContentTypes = []` 也救不了；但 `AVAudioFile` 能正常读、QuickTime 能播。重建一份（`cp` + `mv`，新 inode）即恢复。给这个场景留了一条不走面板的入口：⌘C 复制 + 菜单「转写剪贴板里的音频」（2026-11-04 / 1.3.5）
- **wav 头里的长度字段不可信**：录音笔/手机/边录边写的程序常把 `data` chunk 长度写成 `0`，`AVAudioFile` 会严格按声明读 → 0 帧 → 看起来「文件不认识」。读之前按实际文件大小把 `RIFF` / `data` 两处长度改写（副本，不动原件），只在声明 `0` 或大于实际剩余时才动（2026-11-04 / 1.3.4 修；实测把「喂入 0 块」救回「喂入 30 块、31 字」）
- 语音这条链路整体 `@available(macOS 26.0, *)` 隔离在 `SpeechRunner` / `MemoSession` 里，系统低于 26 只提示不支持，不影响投放和截屏
- 面板状态是一个 `MemoUI` 枚举（idle / preparing / recording / transcribing），由 `renderMemo` 统一渲染；录音时实时文字走 `onUpdate` 回调，主线程 10Hz 节流，麦克风回调线程只做转码和 yield
- 录音期间禁用截屏按钮：面板本来就要临时收起，拍完再恢复会打乱录音界面的节奏
- **「投递」不能挂在会死的对象上**：`MemoSession` 在 `endMemo()` 里被置空，转写任务结束即释放，而 `DispatchQueue.main.async { [weak self] }` 里那块闭包是**之后**才执行的 → 结果被当成「会话已释放」丢掉。会话活多久只该决定进度画不画，**结果送达必须自带强引用**（`MemoDelivery.post`）（2026-11-04 / 1.3.14 修，现场日志里「交付结果」与「丢弃 done」同一毫秒就是它）
- **删文件必须排在「确认写成功」之后**：1.3.13 是「转写完 → 删录音 → 投递结果」，投递一失败，文字和录音同时没了。任何「先清理再交付」的顺序都要反过来（2026-11-04 / 1.3.14）
- **转写结果要先落盘再交付**：`pending/<UUID>.json`，写 `.tmp` 再 rename，权限 0600。界面只是消费者，不是保管人；进程退出、轮次被顶掉、看门狗恢复都能靠它补写。补写要幂等——串行队列 + 「入队后重新确认 pending 还在」，否则会写出两篇重复笔记（2026-11-04 / 1.3.14，验收时正是这里抓到重复）
- **日志要在对象还活着的时候取**：`RecordingStore.close()` 会把 `format` 置空，而日志在关闭之后才打印 → 永远输出「未建立」，同一行却写着 452 万帧，直接把排查方向带偏。易失的元数据要在打开时固化（2026-11-04 / 1.3.14）
- **「文字覆盖了音频多少」比「出了多少字」有用**：每条定稿结果带 `range`（`CMTimeRange`），取并集算覆盖秒数与最长空白。94 秒音频只出 51 字时，覆盖率能把「本来没说几句」和「丢了一大半」分开（2026-11-04 / 1.3.14 加）
- **验收阈值可调时，前面的门槛也要跟着降**：看门狗原来 `guard silent >= 20`，把 `OBSIDIANDROP_STALL_SECONDS=10` 完全挡住，注入的阈值形同虚设 → 门槛写成 `min(20, stallRecoverSeconds)`。排查工具自己不能骗人（2026-11-04 / 1.3.14 修）
- **「不产生文件」的分支不能走「必须有文件」的判定**：`--shot clipboard` 成功时返回 `ok=true, file=nil`，CLI 却用 `guard r.ok, let f = r.file` 判成功 → 复制成功反而 `exit 1`，还打印「未截图」（2026-11-05 / 1.3.15 修）
- **子命令的「给了参数却没给值」不能静默降级**：`--shot --target` / `--transcribe --target` 缺值时原来会退回「上次用的目标」，等于把笔误投到别的目录。与 `--file` 统一成 `exit 2` 且不产生副作用（2026-11-05 / 1.3.15 修）
