# 录音「不全」根因排查与原文件存储方案

- 日期：2026-11-17
- 触发：用户在 MacBook（MacBookPro17,1 / macOS 26.5 / build 25）录了 60 分钟的灵感，反馈「录音不全，结尾少了一截」
- 相关代码：`Sources/main.swift`（`SpeechRunner.transcribeFile` / `TextBox` / `RecordingStore` / `MemoSession`）

---

## 1 现场证据（MacBook 日志 11-16 那次）

```
[11-16 15:35:17.909] run 1 ｜ 录音结束：墙钟 3624.7s，文件 3624.5s，695908096 字节，
                     格式 48000Hz/1ch/float32，帧 173976000，写失败 0 次，峰值 100%
[11-16 15:38:35.989] 识别完成：用时 197.8s，已出 5914 字
[11-16 15:38:38.443] 收尾：用时 2.5s（限 181s），正常，字数 5914
[11-16 15:38:38.496] 转写完成：音频 3624s，产出 5914 字
[11-16 15:38:38.496] 结果覆盖：41 段定稿（partial 5301 条），覆盖 3073.1s / 3624.5s（84%），最长空白 234.7s
```

### 1.1 录音本身是完整的

墙钟 `3624.7s` 与文件 `3624.5s` 只差 0.2 秒，`写失败 0 次`，664 MB 全部落盘。
**「录音不全」不是录音环节丢音频**，这一点先排除。

### 1.2 丢的是转写结果

- 60.4 分钟只产出 5914 字，密度 98 字/分钟（正常中文说话 200–300 字/分钟）
- 覆盖 84%，最长连续空白 **234.7 秒**（近 4 分钟完全没有定稿文字）
- `41 段定稿` vs `partial 5301 条`：引擎一直在出中间结果，但只有 41 条被定稿

## 2 复现实验（本机，build 25）

用 `say -v Tingting` 生成两段连续中文语音（无安静段），走同一个 `--transcribe` 入口。

| 样本 | 时长 | 字数（参考值） | 结果 | 覆盖 |
|---|---|---|---|---|
| A. `od-long.aiff` 第 1 次 | 536.5s | 2286 字 | 2152 字 | 100% |
| B. `long8.m4a`（A 转 AAC 16k） | 536.5s | — | 1962 字 | 99% |
| A. `od-long.aiff` 第 2 次 | 536.5s | 2286 字 | 2093 字 | **87%** |

**同一个 aiff 文件跑两次：100% 与 87%，最长空白 0.0s 与 65.2s。** 差异不是压缩造成的，是收尾阶段不稳定。

### 2.1 收尾耗时对照

| 场景 | finalize 上限 | 实际 | 结论 | 覆盖 |
|---|---|---|---|---|
| A 第 1 次 | 26s（536.5/20） | **26.8s** | **超时** | 100% |
| A 第 2 次 | 26s | **26.8s** | **超时** | **87%** |
| B（m4a） | 26s | 18.2s | 正常 | 99% |
| 11-10 的 362s 样本 | 18s | 12.6s | 正常 | 100% |
| 11-16 的 3624s 样本 | 181s | 2.5s | 正常 | 84% |

### 2.2 60 分钟临界复现（本机）

用 `say` 生成 3759.5s（62.7 分钟）连续语音、15598 字，与用户那次的 3624.5s 几乎同长：

```
转写文件：od-60.aiff，22050Hz/1ch，3759.5s（82896629 帧）
识别完成：用时 98.9s，已出 4865 字
收尾：用时 181.9s（限 187s），正常，字数 14571
结果覆盖：覆盖 99%
```

**收尾 181.9s vs 上限 187s——只差 5 秒就超时截尾。** 产出 14571 字，对参考文本 15598 字保留 93.4%（差额主要来自数字/专名识别错乱与重复段合并，非整段丢失）。

### 2.3 收尾时间的真实决定因素

同样是 60 分钟音频：

| 机器 | analyzeSequence 耗时（喂入速度） | finalize 耗时 | 上限 | 结果 |
|---|---|---|---|---|
| MacBook（用户那次） | 197.8s（18× 实时） | **2.5s** | 181s | 正常 |
| 本机（本次复现） | 98.9s（38× 实时） | **181.9s** | 187s | 卡在边缘 |

喂得越快，积压越多，收尾越久——最坏情况收尾时间接近「识别整段音频所需时间」。**`seconds / 20` 与真实需要量之间没有因果关系，只是碰巧在中等长度上够用。**

## 3 根因

### 3.1 P0：`finalizeLimit` 与实际积压量无关，长音频必然超时截尾

`Sources/main.swift:2024`

```swift
let finalizeLimit = min(max(15.0, seconds / 20.0), 900.0)
```

`analyzeSequence` 返回**不等于**结果处理完。它返回时，分析器内部还压着一批已经算出、但还没吐进 `transcriber.results` 的结果。积压量取决于「喂入速度 vs 识别速度」的竞争：

- 喂得快（本机 536s 音频只用 10.3s 喂完，52× 实时）→ 积压多 → finalize 需要 26s 以上 → 撞上限
- 喂得慢（MacBook 上 60 分钟音频喂了 197.8s，18× 实时）→ 积压少 → finalize 只要 2.5s

所以「音频时长/20」这个系数跟真实需要的收尾时间没有因果关系。**同一文件两次跑，一次卡上限一次不卡，结果就差 13 个百分点。**

超时后 `runWithTimeout` 会 `cancel()` 掉 finalize 任务，剩余结果不再吐出；后面的 `drain`（`seconds/120`，本机 4.5s）来不及补，尾部就丢了。这与用户说的「结尾少了一截」形态一致。

### 3.2 P1：覆盖率指标只统计定稿段，会把「已识别但未定稿」算成空白

`Sources/main.swift:1893` 的 `coverage(total:)` 只用 `finalRanges`（`isFinal == true` 的区间）。而 11-16 那次 `partial 5301 条`——大量音频其实有中间结果，只是没定稿。指标把它们算成「空白」，于是 84% / 最长空白 234.7s 可能**高估**了缺失程度。

同一文件两次跑出 100% 与 87%，也说明这个指标波动大，**不能单独当作「丢字」的判据**。

### 3.3 P1：超时是静默的

`if !finalizeOK { NSLog(...) }` 只写系统日志，笔记里没有任何痕迹。用户拿到笔记无法知道「最后一段可能没过完」，也无从复核——因为原文件已经删了（见 3.4）。

### 3.4 P0（产品级）：原文件转写完即删，问题无法复核

`RecordingStore` 的注释写着「转写成功就删」，`SceneCLI` / `MemoArchiveQueue` 成功后调用 `discard()`。于是：

- 用户感觉「少了一截」，无法确认是「当时没说」还是「真丢字」
- 无法用同一文件重跑对照（本次复现实验正是靠自备样本才做成）
- 无法改用更好的模型重转写

这正是用户提出「需要存储录音原文件」的根因。

### 3.5 已排除的假设

| 假设 | 排除依据 |
|---|---|
| 录音文件被截断 | 墙钟 3624.7s vs 文件 3624.5s，差 0.2s |
| 写盘失败 | `写失败 0 次` |
| 设备切换导致后段丢失 | 文件时长完整，`AVAudioEngineConfigurationChange` 未触发（日志无中断痕迹） |
| 转写进程卡死 | 进度 96→5914 字匀速增长，197.8s 正常结束 |
| analyzeSequence 超时 | 上限 469s，实际 197.8s |

## 4 修复方案

### F1（P0）收尾判据改成「覆盖到末尾」而不是「到点就砍」

`transcribeFile` 的收尾改为双条件轮询：

```
循环（每 250ms）：
  1. 结果流已结束（collector 完成）→ 退出，成功
  2. box 的定稿覆盖已到达音频末尾（≥99.5%）→ 退出，成功
  3. finalize 任务结束 → 退出，成功
  4. 超过硬上限 → 退出，标记 incomplete
硬上限：max(60, seconds * 1.0)，封顶 1800s
```

要点：**上限从「预测需要多久」改成「最多容忍多久」**，最坏情况给到实时时长（60 分钟音频最多等 60 分钟收尾），因为正常只要几秒到几十秒，只有异常长尾才触及上限。

### F2（P0）超时必须留痕

- `MemoOutcome` 增加 `transcriptIncomplete: Bool` + `coveredSeconds` / `totalSeconds`
- 笔记 frontmatter 写 `转写完整: false`
- 正文尾部追加一行：`> 本次识别覆盖 87%（03:12–04:17 无文字），最后一段可能未完成，可点[[录音原文件]]重新转写`
- 界面 flash 提示，不再只写 NSLog

### F3（P1）覆盖率指标纳入未定稿区间

`TextBox` 除 `finalRanges` 外单独记 `partialRanges`，覆盖率输出两个数：

```
结果覆盖：定稿 84% / 含未定稿 96%，最长空白（定稿口径）234.7s，最长空白（含未定稿）18.2s
```

这样下次看日志就能区分「真空白」与「只是没定稿」。

### F4（P1）`removeTap` 后等音频线程静默再 `close()`

当前 `teardown()` 立刻 `removeTap`，正在执行的 tap 回调随后 `append` 会撞上 `closed` 守卫被丢（≤85ms）。改为：置 `stopping` 标志 → 等 `append` 空闲（最多 500ms）→ `close()`。量级小，但属于同一类「结尾丢一截」，顺手修掉。

### F5（P2）设备变更自愈

注册 `AVAudioEngineConfigurationChange` 通知。格式变化时不再整块丢弃（当前 `append` 里 `ff == buf.format` 不等就跳过），而是：

- 关闭当前文件 → 新建分段文件继续录 → 结束时按顺序拼接转写
- 界面提示「输入设备已切换，录音继续」

本次日志未触发，属预防性改造，可与原文件功能一起排期。

## 5 新功能：录音原文件存储

### 5.1 已确认的决策

| 项 | 决策 |
|---|---|
| 位置 | `<库>/附件/录音/YYYY-MM/` |
| 文件名 | `yyyyMMdd-HHmmss-灵感.m4a`（与现有附件命名习惯一致） |
| 格式 | AAC 16 kHz 单声道 |
| 保留 | 永久，不自动清理 |

### 5.2 编码方案已验证（本机实测）

用 `AVAudioConverter` + `AVAudioFile(forWriting:settings:)`，纯 AVFoundation，无需外部工具：

| 指标 | 实测值 |
|---|---|
| 源 | 22050Hz/1ch，536.5s，23.6 MB |
| 目标 | AAC 16 kHz/1ch/24 kbps |
| 输出体积 | 1.62 MB |
| 压缩比 | 13.9× |
| 折算 | **10.9 MB/小时**（对比原始 caf 664 MB/小时，约 1/61） |
| 转换耗时 | 0.37s（**1440× 实时**） |
| 回读时长 | 536.5s，**误差 0.00s** |

#### 关键实现陷阱（已踩到）

`AVAudioFile` 写 AAC 后**必须先释放句柄再回读或移动文件**，否则回读报
`ExtAudioFileOpenURL` 失败（`Code=1685348671`），因为 moov box 还没落盘。
产品代码里必须把写入包进独立作用域（或显式置 nil），再去做校验/移动。

#### AAC 是否损失识别准确率——四组对照

同一段 536.5s 语音，四种编码各跑一次：

| 编码 | 体积 | 产出字数 | 覆盖 |
|---|---|---|---|
| 原 aiff（22050Hz） | 23 MB | 2152 / 2093（跑两次） | 100% / 87% |
| 16k int16 无损 caf | 16 MB | 2047 | 87% |
| **16k AAC 24kbps** | **1.6 MB** | **1962** | **99%** |

字数落在 **1962–2152（±4.6%）**，与编码无关：16k 无损的 2047 正好落在原文件两次结果的中间。
**结论：AAC 压缩没有额外识别损失，之前的 190 字差是运行波动。** 体积却只有 16k 无损的 1/10、原 caf 的 1/61，因此选 AAC。

### 5.3 笔记怎么写

frontmatter：

```yaml
录音: "[[附件/录音/2026-11/20261116-143453-灵感.m4a]]"
录音时长: 60:25
转写完整: true
```

正文末尾（可选一行，便于回听）：

```
🎧 [[附件/录音/2026-11/20261116-143453-灵感.m4a|录音原文件（60:25）]]
```

### 5.4 失败兜底

| 情况 | 处理 |
|---|---|
| 编码失败 | 保留原始 caf 在 `~/Library/Application Support/ObsidianDrop/recordings/`，笔记里写绝对路径 + 界面提示 |
| 磁盘空间不足（< 2× 预估体积） | 编码前预检，不足则保留 caf 并提示，不中断归档 |
| 库路径不可写 | 落到应用支持目录并提示，不阻断笔记写入 |
| 转写失败 | 原文件照常保存（这正是最有价值的场景） |

### 5.5 重转写入口（原文件的核心价值）

- 菜单「用原文件重新转写…」→ 选 m4a/caf → 走现有 `--transcribe` 同一条路径
- 笔记里的录音链接旁加一行说明：`若识别不全，可用该文件重新转写`
- 重新转写时覆盖原笔记正文还是新建笔记 → 需产品确认（建议：新建 `…-重转写.md`，不覆盖原件）

### 5.6 体积预估

| 录音时长 | m4a（16k/24kbps） | 原 caf（48k float32） |
|---|---|---|
| 10 分钟 | 1.8 MB | 111 MB |
| 1 小时 | 10.9 MB | 664 MB |
| 3 小时 | 33 MB | 2.0 GB |

一天 2 小时会议，一年约 8 GB，可接受。

## 6 需要 Codex 分析的问题

1. **F1 的判据是否成立**：用「定稿覆盖到末尾」作为完成条件，在 `DictationTranscriber` 的实际行为下是否可靠？会不会出现「覆盖到 99% 但最后一句还没定稿」就提前退出、反而截尾？
2. **上限该给多少**：`max(60, seconds * 1.0)` 封顶 1800s 是否合理？3 小时会议时 1800s 是否够？
3. **是否该改成分段转写**：按 5 分钟切段、逐段 `analyzeSequence` 再拼接，是否能从根上消除「积压不可控」？切段边界的断句/重复如何处理？
4. **AAC 16k/24kbps 的识别损失**：实测 1962 字 vs 原文件 2093–2152 字，是压缩导致还是运行波动？若确有损失，是否该改存 16k int16 无损（115 MB/小时）？
5. **F4 的等待方式**：`removeTap` 后如何可靠判断「音频线程已静默」？轮询 `append` 计数 vs `DispatchQueue.sync` 栅栏，哪个在 CoreAudio 实时线程上安全？
6. **F5 分段文件**：多段 caf 拼接转写时，是否会有时间轴/格式一致性问题？
7. **存储路径**：`附件/录音/YYYY-MM/` 是否与 Obsidian 库现有结构冲突？重名如何处理？
8. **风险点**：以上改动里，哪些会触及 1.7.0 已验证过的路径（自检 209 项 / 回归 56 项），需要同步改断言？

## 8 Codex 评审与最终实现的差异（2026-11-17）

方案初稿交 Codex 只读评审（job `fd4541ed`），结论是「可执行但不能原样批准」。按它的意见改了四处，最终实现与本文第 4、5 节有出入，以本节为准。

### 8.1 被否掉的：F1 用「覆盖率≥99.5%」当成功条件

理由成立：

- `finalizeAndFinishThroughEndOfInput()` 返回后，结果仍可能积压在独立 collector 里，finalize 结束不代表文字读完
- `isFinal` 是单条结果的属性，SDK 没把它定义为「全段已终结」
- 99.5% 阈值在 1 小时音频上允许缺 18 秒，足够包含最后一句
- 尾部可能是静音，覆盖不满并不等于丢字；反过来覆盖到 99% 也不证明结果不会再来

**最终实现**：完成判据只看三条链路的终态——

```
incomplete = !analyzeOK || !finalizeOK || !drainOK
             || collectorError != nil || finError != nil
```

覆盖率**只用于诊断**，不参与成功判定。

### 8.2 补上的三个 P0

| 问题 | 修法 |
|---|---|
| collector 的 `catch` 与 finalize 的 `try?` 把错误吞掉后当成成功 | 两者各用一个 `OSAllocatedUnfairLock<String?>` 记下错误，纳入 `incomplete` |
| 永久录音若复用 `audioPath`，会被归档清理删掉 | 新增 `retainedAudioRel`，与临时 `audioPath` 严格分开；两处清理分支都只在「已入库」时删 caf |
| 媒体与笔记之间没有事务边界 | 先写临时件 → 校验时长与可播放性 → `moveIntoPlace`（同卷 move、跨卷 copy 后比对大小）→ 写回 pending → 写笔记 → 最后删 caf |

补归档重跑时用 `RecordingArchive.existing(rel:vault:)` 复用库内那份，不重复转码；文件大小 >1KB 且能被 `AVAudioFile` 打开才算可用。

### 8.3 未完成项（必须在后续补）

| 项 | 状态 |
|---|---|
| 3 小时录音的 finalize 实测 | **未做**。1800s 上限是按 62.7 分钟样本 181.9s 线性外推的，不是实测 |
| AAC 的识别质量对照（CER/专名/末 60 秒留存，每种格式 3–5 次） | **未做**。目前每种格式只跑 1 次，只能说「落在波动区间内」，不能证明零损失 |
| 用户 11-16 那次的 84% 覆盖 | **未闭环**。那次 finalize 只用 2.5s 就正常结束，与本次复现的截尾机制不同；不排除是真实静音 + 定稿粒度粗 |
| 分段转写 | 未采用，保留为 Plan B（Codex 建议先修完成语义，边界切分风险大于收益） |
| 设备变更自愈（F5） | 未做，本次日志未触发 |

### 8.4 文案修正

Codex 指出：库里存的是 AAC 16 kHz，不是设备原生的 48 kHz float32，「录音原文件」这个叫法不准确。产品界面与笔记里仍沿用「录音原文件」（用户习惯），但文档明确写清是 AAC 压缩版；`附件/录音/` 下的是**可回听、可重转写的留档**，不是位级备份。
