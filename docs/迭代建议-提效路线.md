# ObsidianDrop 迭代建议：把「记录成本」和「找回成本」继续压低

> 基线 1.3.15（构建 19）｜2026-11-05
> 本文由「我做初判 → Codex 独立复核（21 项）→ 我逐条取舍」合成。标 ⚑ 的是 Codex 提出、我原先漏掉的。

## 一、现在时间花在哪

一句话：**东西进库很快（秒级），但"触发"和"事后找"还得靠人。**

| 环节 | 现在 | 成本 |
|---|---|---|
| 触发 | 移到菜单栏 → 点图标 → 点菜单项 | 2–3 秒，且打断思路 |
| 投递 | 拖拽或自动 | ≈ 0 |
| 选目标 | 靠人记得先切「投递目标」 | 忘切就进错目录，事后要搬 |
| 归档后 | 自己去收件箱找那篇 | 5–20 秒 |
| 事后整理 | 灵感散在收件箱，没有汇总 | 每周集中一次 |
| 出问题 | 找日志、复制、发给我 | 2–3 分钟 + 一轮往返 |

四个方向：**触发更短（热键）→ 判断更少（预测/预览）→ 找得更快（索引/汇总）→ 排障更省（诊断包/队列面板）。**

## 二、A 档：小改动、马上能感觉到（建议 1.3.16 一起做）

| # | 功能 | 瓶颈 | 实现要点 | 风险 | 验收 |
|---|---|---|---|---|---|
| A1 | **全局快捷键**：`⌥⌘R` 录音开/停、`⌥⌘S` 区域截图、`⌥⌘V` 剪贴板文本 | 每次都要去找菜单栏图标，2–3 秒 | Carbon `RegisterEventHotKey`（不需要辅助功能权限，比 `NSEvent` 全局监听干净）；偏好键 `hotkeyMemo/hotkeyShot/hotkeyClip`；冲突时菜单里提示 | 与系统/其他 App 热键冲突；误触产生 <1 秒空录音（现有 `<0.6s` 判据可挡） | 自检：热键字符串解析 + 冲突检测；手动：任意 App 前台按 `⌥⌘R` 出现「准备中」 |
| A2 | **剪贴板文本入库** | 最高频的其实是"复制一段文字"，而现在只能截图/拖文件/说话 | 新增 `Filer.note(text:target:source:)`，复用 `Filer.memo` 但去掉时长；入口：热键 + 菜单项。正文前记一行来源 App | 可能复制到密码/验证码 → 不记窗口标题，菜单可关 | 自检：给定字符串 → 笔记含 `类型: 剪贴片段`；空/纯空白不写文件 |
| A3 ⚑ | **待归档队列面板**（可视 + 手动重试） | 1.3.14 已保证结果落盘，但用户只能等看门狗或重启 | 菜单「待归档结果…」：列出 id / 目标 / 时间 / 录音是否存在 / 尝试次数，按钮调用 `MemoArchiveQueue.archive`；重试必须走同一串行队列 | 与后台 drain 并发 → 复用 `claim` 逻辑；**不显示正文**（只有字数） | `OBSIDIANDROP_DROP_DONE=1` 跑完后队列有 1 条 → 手动重试成功 → 最终只有 1 篇笔记 |
| A4 | **一键诊断包** | 出问题时我要用户找日志、报机型版本，来回 2–3 轮 | 菜单「导出诊断包…」+ `--diagnostics <zip>`：日志尾部 2000 行、版本/机型/系统、`--audio-check --json`、pending 清单（只 id/字数/时间）；**不含正文** | 目录名与原路径属隐私 → 打包前在弹窗里列明包含哪些文件 | 自检：解包后 4 类文件齐全，且 pending 摘要里搜不到正文哨兵字符串 |

> A3 与 A4 可以合成一个「状态面板」：上半是待归档队列，下半是「导出诊断包」按钮。

## 三、B 档：明显提效，但要动一点结构（1.3.17 ~ 1.4.0）

| # | 功能 | 瓶颈 | 实现要点 | 风险 | 验收 |
|---|---|---|---|---|---|
| B1 | **归档后写一行到当日索引** | 归档完还得去收件箱翻，一天下来不知道收了什么 | `DailyIndex.append`：`日记/YYYY-MM-DD.md`（路径可配）末尾追加 `- HH:mm [[笔记]] → 目标`；不存在则创建；失败不影响主流程 | 与 Periodic Notes 抢同一文件 → 只追加不重排；并发写要串行 | `--ui-memo` 跑完日记多一行；连跑两次不重复（按 wikilink 去重） |
| B2 ⚑ | **投递前预览（dry-run）** | 投错目标才发现，事后要搬文件、改 frontmatter | `--file --dry-run` + 菜单「看会放到哪」：复用 `VaultGuard/ArchiveTarget/uniqueURL`，只算不写 | 预测名与并发投递后的实际唯一名可能不同 → 文案写「预计」 | 自检：收件箱/项目/非法目标/越界软链四种预测；回归后库内文件数与 mtime 未变 |
| B3 | **多库切换** | 工作库/个人库现在只能 `--vault` 临时覆盖 | 菜单「库」子菜单：最近 3 个库 +「选择其他…」；`targetRel` 与窗口位置按库分别记忆；**切换前排空**（非 idle 时禁用） | 同名库要区分（用路径而非目录名）；旧 pending 不能被改投 | 切库后投递落在新库；在 A 库生成的 pending 切到 B 后仍回 A |
| B4 ⚑ | **共享导入目录（手机/下载器的入口）** | 手机录音、下载器成果仍需手工拖 | 扫描/监视一个独立 Inbox 目录（如 `~/ObsidianDrop-Inbox`），出现文件即投递到指定目标，成功后移到 `已处理/` | iCloud 占位文件（未下载）需跳过重试；重复处理 | 回归：放两个文件各处理一次；重启不重复；占位文件不误判 |
| B5 ⚑ | **稳定错误码** | 现在错误文案适合人读，脚本无法稳定判断（模型下载 / TCC / 路径 / 磁盘） | `MemoError`/`FilerError` 增加 `code`（`speech_denied`、`vault_missing`…），日志与 `--json` 都输出；原中文文案保留 | 兼容旧脚本 → 只新增字段不改原字段 | `--file --json`、`--transcribe` 分别断言 `code=...`，旧字段仍在 |
| B6 | **目标排序与记忆** | 项目多了目标菜单很长，每次要扫一遍 | 按使用频次排序，最近 3 个置顶；频次写 `targetUsage` | 顺序变动破坏肌肉记忆 → 只置顶 3 个，其余仍字母序 | 连投 3 次 P1 后 P1 出现在置顶区 |

## 四、C 档：有价值但要看实际使用频率（1.4.x）

| # | 功能 | 瓶颈 | 实现要点 | 风险 | 验收 |
|---|---|---|---|---|---|
| C1 ⚑ | **内容哈希去重** | 同一文件换个名字再投一次，库里多一份 | `Filer.archive` 算 SHA-256，命中则提示「库里已有 `<笔记>`」；默认**仍不删除**，显式 `--dedup` 才跳过 | 同内容可能确实要两份 → 只提示不阻断；大文件算哈希有成本 | 自检三组：同内容同名、同内容异名、异内容同名；`--json` 输出 `duplicate_of` |
| C2 | **批量转写队列** | 会议录音攒几个只能一个个点 | `--transcribe-queue <目录>` 或菜单多选；复用 `--ui-memo` 的自动链路，顺序跑，失败不阻塞 | 长队列占内存（`SpeechAnalyzer` 需及时释放）；加 1 秒间隔 | 3 个文件 → 3 篇笔记 exit 0；中间一个坏文件 → 其余完成、exit 3 |
| C3 | **模板可配** | 项目要求固定小标题，现在模板写死 | 偏好 `noteTemplate` 指向 md 文件，只认 `{{title}} {{date}} {{target}} {{link}}`；渲染失败回退内置 | 与 Templater 语法不同 → 文档写明不执行任何表达式 | 自检：4 个占位符渲染齐全；模板缺失回退且日志留痕 |
| C4 | **规则式行动项 / 标签** | 灵感稿是整段话，事后自己挑"要做的事" | 纯规则：目标映射标签、"要/需要/记得/明天"开头句 → `- [ ]`；**只追加 `## 下一步`，不动正文** | 误判 → 原文永不动；模型路径（`FoundationModels`）必须可降级 | 自检 10 句样例的抽取结果；模型不可用时日志写「降级为规则」 |
| C5 ⚑ | **项目 MOC 维护** | Dataview 之外还要手工找每个项目的投递与灵感 | 显式「更新项目索引」动作，读 frontmatter 生成独立 MOC；**不每次投递都写** | 并发写同一 MOC、iCloud 冲突 | 连续更新两次幂等；投递后旧条目不重复 |
| C6 ⚑ | **启动恢复摘要** | 用户不知道后台补写成功没有 | `drain()` 返回 `ok/failed`，启动后浮窗提示一次 | 反复打扰 → 只提示一次，失败可直接打开日志 | 构造 2 成功 1 失败 → 摘要 `ok=2 failed=1` |

## 五、D 档：先不做（写下来避免反复讨论）

| 功能 | 为什么不做 |
|---|---|
| 录音期间实时出字 | 1.3.11 正是为稳定性才改成"先落盘再转写"；恢复实时出字等于重开一路并发分析，1.3.12–1.3.14 修过的竞态会回来。要做也只能是默认关闭的实验开关 |
| 默认双向改写笔记 / 待办 | 自动改用户笔记是最高风险操作；先做只读视图（Dataview 已经够） |
| 说话人分离 | 端上无稳定 API，要么引第三方模型（违背零依赖），要么上云（违背隐私承诺） |
| 自建同步 | Obsidian 已有 iCloud / 官方 Sync / Remotely Save |
| 内嵌 Obsidian 插件桥 | 依赖插件 API 与版本，升级即碎；文件契约更耐久 |
| 原子独占命名（并发安全） | ⚑ Codex 提的，技术上对；但实际是单实例使用，优先级低于上面所有项。**建议只在文档里写明"多实例并发不保证"**，等真出现多实例场景再做 |
| 跨进程 pending 锁 | ⚑ 同上：单实例没有这个问题；真要多开，先禁多开（`LSMultipleInstancesProhibited`）比加锁便宜 |

## 六、如果只做三件

1. **A1 全局快捷键** —— 触发从 2–3 秒降到 0.3 秒，唯一"每天都省"的改动。
2. **A2 剪贴板文本入库** —— 补齐最后一种输入形态（文字），实现量最小（复用 `Filer`）。
3. **A3+A4 状态面板（队列 + 诊断包）** —— 省的不是用户时间，而是**每次排障的往返轮次**；1.3.13/1.3.14 两轮定位全靠用户手工发日志。
