## 0. 一句话结论

四条建议里，**1 和 4 是同一件事**（菜单栏入口重做），**2 依赖 1**（搜索结果要有地方显示），**3 是前两条的地基**。建议合成两个版本：1.3.16 做「入口」，1.4.0 做「搜索」。理由：先改入口能立刻降低日常成本，且搜索面板正好挂在新入口上，不用二次改布局。

### 3.2 关键结论：`canBecomeKey = false` 会直接卡死搜索

无边框 `NSPanel` 若不能成为 key window，内部的 `NSTextField` 收不到键盘事件——搜索框可以画出来、可以点，但打不进字。这不是「可能有问题」，是必然。

正确做法（1.3.16 就要改，否则 1.4.0 得推倒重来）：

```swift
final class DropPanel: NSPanel {
    override var canBecomeKey: Bool { true }   // 收键盘
    override var canBecomeMain: Bool { false } // 不做主窗口
}
```

配合保留 `.nonactivatingPanel`：面板能拿键盘，但不会把前台 App 变成非活跃——这是 Raycast / Alfred 同类面板的标准做法。风险：成为 key window 后输入法候选框、`Esc`、Tab 焦点行为都会变，必须实测（见 §7 验收）。

### 3.3 状态机（Codex 复核后重写）

模式：`PanelMode { dropdown, docked }`，存 UserDefaults 新键 `panelMode`。

| 当前状态 / 事件 | 下一状态 | 持久化与窗口行为 |
|---|---|---|
| 新装启动，无任何旧偏好 | `.dropdown` + hidden | 不恢复常驻窗口，首次左键显示下拉 |
| 升级启动，**存在 `panelVisible` / `panelX` / `panelY` / `panelBottom` / `targetRel` / `vaultPath` 任一旧键** | `.docked` + 恢复 `panelVisible` | 写入 `panelMode=docked` 作为迁移标记 |
| `.dropdown` 左键 | visible ↔ hidden | **不写 `panelVisible`**（临时可见不能变成下次启动偏好） |
| `.dropdown` 拖动超过 2px 阈值并**松手** | `.docked` + visible | **必须在 mouseUp 才切**，mouseDown/首次移动就切尺寸会造成窗口跳动与锚点漂移 |
| `.docked` 左键 / 菜单「面板」 | visible ↔ hidden | 沿用 `setPanelVisible()` |
| 设置里选「恢复菜单栏下拉」 | `.dropdown` + hidden | 从 docked 回 dropdown 的显式出口 |
| 点外部 / Esc / 切换 Space（dropdown） | hidden | 移除临时监视器，保留模式 |

两处必须跟着改：

- `togglePanel()`（main.swift:3423-3425）改为按模式分派：docked → `setPanelVisible`，dropdown → `showDropdown/dismissDropdown`。
- `applyWindowLevel()`（main.swift:3428-3435）按 `(panelMode, panelBottom)` 决定：**dropdown 强制 `.floating`**。否则用户开着「窗口置于底层」时，下拉面板会压在所有窗口后面，等于点不出来。

> 两个模式共用同一个面板实例，只改尺寸与锚定策略，不新建两套窗口——两个窗口会带来焦点、层级、Exposé 三处不一致。

### 3.4 双触发实现（Codex 版，比我的草稿干净）

核心规则：**`statusItem.menu` 永久保持 `nil`，菜单按需生成**。不反复挂摘，也不调 `performClick`——我原来的写法（临时挂上再摘掉）依赖 `performClick` 同步阻塞，容易残留状态。

```swift
private enum PanelMode: String { case dropdown, docked }
private var panelMode: PanelMode = .docked
private var popupMenu: NSMenu?

private func buildStatusItem() {
    statusItem = NSStatusBar.system.statusItem(withLength: NSStatusItem.variableLength)
    if let b = statusItem.button {
        b.image = NSImage(systemSymbolName: "tray.and.arrow.down.fill",
                          accessibilityDescription: "ObsidianDrop")
        b.image?.isTemplate = true
        b.target = self
        b.action = #selector(statusItemClicked(_:))
        b.sendAction(on: [.leftMouseUp, .rightMouseUp])
    }
    statusItem.menu = nil          // 永久置空
    rebuildMenu()                  // 只刷新 popupMenu 缓存
}

@objc private func statusItemClicked(_ sender: NSStatusBarButton) {
    guard let event = NSApp.currentEvent else { return }
    switch event.type {
    case .leftMouseUp:  togglePanel()                       // 按模式分派
    case .rightMouseUp: presentMenu(with: event, in: sender)
    default: break
    }
}

private func rebuildMenu() { popupMenu = makeMenu() }
private func makeMenu() -> NSMenu { /* 新精简菜单 */ }

private func presentMenu(with event: NSEvent, in view: NSView) {
    let menu = popupMenu ?? makeMenu()
    NSMenu.popUpContextMenu(menu, with: event, for: view)
}
```

**必须同步改面板右键**（main.swift:3391-3394）。那里现在直接读 `statusItem.menu`，一旦永久置 nil，面板右键就静默失效：

```swift
dropView.onRightClick = { [weak self] event in
    guard let self else { return }
    self.presentMenu(with: event, in: self.dropView)
}
```

`menuNeedsUpdate`（main.swift:3369-3371）继续有效——`NSMenu.delegate` 在菜单弹出时照常回调，用于刷新投递目标列表。

### 3.5 下拉定位（Codex 修正：返回 frame 而不是 origin）

我原来是 `dropdownOrigin(size:)` 只返回原点。Codex 指出这不够：**窄屏时面板本身放不下，必须连尺寸一起裁**。改为：

```swift
func dropdownFrame(anchor: NSRect?, visible: NSRect, size: NSSize) -> NSRect {
    let w = min(size.width,  visible.width  - 16)
    let h = min(size.height, visible.height - 16)
    guard let a = anchor else {                    // 图标不可得：主屏顶部居中
        return NSRect(x: visible.midX - w/2, y: visible.maxY - h, width: w, height: h)
    }
    let x = min(max(a.midX - w/2, visible.minX + 8), visible.maxX - w - 8)
    return NSRect(x: x, y: visible.maxY - h, width: w, height: h)
}
```

| 边界 | 处理 |
|---|---|
| 多屏 / 副屏负坐标 | anchor 用 `button.convert(button.bounds, to: nil)` 转屏幕坐标；屏幕取 `button.window.screen.visibleFrame`；**禁止 `NSScreen.main`** |
| 刘海 | 以按钮实际 anchor 为水平中心，再夹到同一屏 `visibleFrame`；顶部由 `visibleFrame.maxY` 保证 |
| 菜单栏自动隐藏 | 用户能点到图标时菜单栏已显示，直接用按钮所在 window 的 screen，不用缓存的历史主屏尺寸 |
| 全屏 Space | dropdown 用 `.canJoinAllSpaces + .fullScreenAuxiliary`；**去掉 `stationary`**（它对瞬态面板是粘滞语义，会让面板留在旧 Space） |
| 切换 Space | 监听 `NSWorkspace.activeSpaceDidChangeNotification` → 立即收起，下次点击按新 Space 重新定位 |
| 点外部收起 | 显示期间装全局 `[.leftMouseDown, .rightMouseDown]` 监视器；点不在 `panel.frame` 与状态按钮内则收起，收起时移除 |
| Esc | `canBecomeKey` 改 true 后，用 local `keyDown` monitor 捕获；**不能指望 `cancelOperation`** |
| 窄屏 / 矮屏 / 屏幕变化 | 尺寸与位置同时 clamp；监听 `NSApplication.didChangeScreenParametersNotification` 重校验 |

> 我原来的 `dropdownOrigin(icon:visible:size:)` 已用 6 组用例跑通（右上角/左上角/副屏/图标不可见/窄屏/顶部贴合）。Codex 认为「仓库里没有这些用例，不能计入验收」——这点它说得对：那 6 组是我在 `/tmp` 临时验证的，要计入验收必须写成 `--self-test` 里的正式断言。

### 3.6 下拉面板尺寸

`160 × 176`（现有）放不下搜索框 + 结果列表。**但 1.3.16 里还没有搜索**，所以尺寸策略要分两步：

| 版本 | 尺寸 | 说明 |
|---|---|---|
| 1.3.16 | docked `160×176` / dropdown `360×172` | 下拉面板只放「投放区（横版 120）+ 动作栏」，**不留空白结果区** |
| 1.4.0 | dropdown `360×432` | 加上搜索框 36 + 结果列表（`NSTableView`，行高 44） |

Codex 明确反对 1.3.16 就发布一块空的结果区——这个意见我采纳：一个占着半屏却什么都没有的面板，比不开下拉更糟。

必须做的结构改动：

| 现状 | 改法 |
|---|---|
| `DropView` 的 icon/title/subtitle/hint/button frame 在 main.swift:2841 一次写死，`layout()` 只重排 ring/border | 拆成 `DropZoneView`（图标、ring、标题、副标题）与 `ActionBarView`（截屏、灵感），两者接收显式高度并在 `layout()` 重排 |

这是 1.3.16 里工作量最大的一块，也是唯一「必须动既有布局」的地方。

> `hitTest` 这条是 Codex 发现的，我原来漏了。它不影响 1.3.16 交付，但会让 1.4.0 的搜索框「看得见点不动」，属于必须提前留好的口子。

## 4. 需求 2：搜索

### 4.1 实测数据（本机，`swiftc -O`）

| 方式 | 41 篇真实库 | 3000 篇 / 10 MB 压测库 |
|---|---|---|
| 全量读取进内存 | 8 ms | 312 ms |
| `String.contains` 单次查询 | 5.7 ms | **180.8 ms** |
| `String.range(.caseInsensitive)` | — | **602.5 ms** |
| **UTF-8 `Data` + `memmem`** | — | **3.1 ms（中文两字）/ 6.3 ms（英文六字）** |
| 内存占用 | — | String 18.9 MB / **完整索引 RSS +31.5 MB**（含小写副本） |
| mtime+size 增量重扫（3000 篇） | — | **9 ms** |

结论：**不做倒排索引，也不上 SQLite**。把库里的 md 以 UTF-8 `Data` 常驻内存，查询用 `memmem` 字节匹配即可——3000 篇下 3–6 ms/次（最坏 5 ms），逐键搜索毫无压力。

内存要说实话：源文件 10 MB，`Data` 各自的分配开销叠上去，**进程 RSS 实际涨 31.5 MB**（我最初按源体积估成 10 MB，错了）。若按 Codex 的建议把小写副本改成懒建，中文检索时不付这 8–10 MB；一旦用户搜过英文关键词，内存回升到 31 MB 量级。规划时按 **20–32 MB** 预留。

我原本也倾向「bigram 内存倒排索引」，实测后否掉：倒排要额外 60–100 MB，收益是把 6 ms 变成 1 ms，不值。

### 4.2 三方案对比

| | 纯 Swift `Data`+`memmem` | SQLite FTS5（trigram） | Spotlight（`NSMetadataQuery`/`mdfind`） |
|---|---|---|---|
| 依赖 | 无 | 系统 `libsqlite3`（`import SQLite3` 实测可用，3.54.0，FTS5+trigram 编译进去了） | 无 |
| 首建 | 312 ms / 3000 篇 | ≈1–2 s | 0（系统已建） |
| 单次查询 | 3–6 ms | <5 ms | 50–300 ms，异步回调 |
| 内存 | **RSS +31.5 MB**（3000 篇 / 10 MB 源） | 独立索引文件（约源体积 1.5–2×） | 0 |
| 中文子串 | 天然支持（字节匹配） | trigram 支持，但需 ≥3 字符 | **差**：按词切分，中文两字常搜不到 |
| 增量 | mtime+size，9 ms 全量重扫 | 需手写触发器/手动同步 | 系统自动 |
| 跨盘 / iCloud 占位 | 只读本地文件，`.icloud` 跳过 | 同左 | 未索引卷直接失效 |
| 额外状态文件 | 无 | 有（坏库要修复/重建） | 无 |
| 工作量 | 小 | 中 | 中（异步 + 去重） |

**推荐：纯 Swift**。淘汰 FTS5 的理由：多一个状态文件和一个坏库修复路径，换来的 5 ms 差距用户感知不到。淘汰 Spotlight 作主检索的理由：中文子串是硬伤（实测 `mdfind "预焙阳极"` 能中，但两字词召回很差），且未索引卷直接失效。

**Spotlight 保留给 1.5.1 的「本地文件」**：那里它无可替代——实测 `mdfind -onlyin ~/Obsidian/Main "预焙阳极"` 能命中附件目录里的 `.pptx` 正文，这是自建索引做不到的。

### 4.3 索引结构（Codex 版：actor + 纯函数分层）

关键改动：**`lower` 改成懒建**。中文查询根本用不到小写折叠，全量常驻等于白付 8.1 MB（Data 从 ~10 MB 涨到 ~18.1 MB）。只有当用户第一次输入含 ASCII 字母的关键词时，才为命中的文档补折叠副本。

```swift
struct VaultDoc: Sendable {
    let url: URL; let rel: String
    let mtime: Date; let size: Int
    let text: Data            // 原文 UTF-8
    let title: Data           // 首行 H1 或文件名
    let nameFold: Data        // 文件名（ASCII 折叠）
    var asciiLower: Data?     // 懒建
}

struct SearchRequest: Sendable { let query: String; let limit: Int; let queryID: UInt64 }
struct SearchHit: Codable, Sendable {
    let rel: String; let title: String
    let rankClass: String        // title | name | body
    let bodyHits: Int            // 非重叠计数
    let mtime: Date
    let startByte: Int; let endByte: Int
    let snippet: String
}

actor VaultIndex {
    init(vault: URL)
    func buildIfNeeded() async throws -> IndexSummary
    func refreshIfNeeded() async throws -> RefreshSummary
    func search(_ req: SearchRequest) async -> [SearchHit]
}

enum VaultIndexer { /* 纯函数扫描器：可注入体积上限，自检直接调，不依赖 actor/GUI */ }
enum VaultSearch  { /* 纯函数：字节查找、非重叠计数、排序、UTF-8 片段 */ }
```

为什么要拆 `VaultIndexer` / `VaultSearch` 两个纯函数枚举：自检里不能起 actor、不能碰真实库，纯函数才能一条一条断言。

| 生命周期 | 做法 |
|---|---|
| 建 | App 启动后第一个 RunLoop 一圈之后，utility 优先级后台建；期间面板显示「索引中」，**不能同步等** |
| 刷 | 面板展开前 `await refreshIfNeeded()`（mtime+size 比对，3000 篇 9 ms）；**每次按键不刷新** |
| 搜 | 只读快照，绝不在搜索函数里碰磁盘 |
| 并发 | actor 串行化建/刷/搜；主线程只收结果；UI 用 `queryID` 丢弃迟到结果 |

> Codex 特别点出一句：「延迟 0.8 秒启动」只是调度策略，不是实测耗时——写方案时别把它当成指标。

### 4.3.1 必须处理的边界

| 边界 | 处理 |
|---|---|
| `.icloud` 占位 | 识别 `.icloud` / 未下载状态，**直接排除，不触发下载**，不等网络 |
| 符号链接 | 目录与文件软链一律跳过（防库外读取、防循环、防重复结果）；自检要造库内、库外两种链接 |
| 超大单文件 | 正文上限 8 MiB；超限仍保留「标题/文件名」命中，标 `too_large`，**不得整文件读入** |
| 二进制假 `.md` | 限体积后做 NUL / 控制字符嗅探；疑似二进制只索引名称，记录原因 |
| 非 UTF-8 编码 | 只接受 UTF-8（含 BOM），不猜 GB18030；正文跳过并报告，文件名仍可搜 |
| 同名文件 | 以库内相对路径为唯一键，跨目录同名**不合并**；mtime 相同用 `rel` 做稳定排序 |
| 片段 | `memmem` 给的是字节区间 → 向两侧扩到 UTF-8 边界 → 解码 → 取命中前后 24 个 `Character`；**禁止出现 `U+FFFD`** |

### 4.5 1.5.1：搜本地文件（Spotlight）

同一面板，搜索框切到「全盘」范围（右侧一个下拉：`库内` / `全部`）。

### 7.2.1 `--search` 契约（Codex 版）

```
ObsidianDrop --search <query> [--vault <path>] [--limit <1...200>] [--json]
```

| 参数 | 规则 |
|---|---|
| `--search` | 必填非空查询。**CLI 冷启动会重新建内存索引**，不能复用 GUI 进程里那 3–6 ms 的已建状态 |
| `--vault` | 缺值 / 路径不存在分别按「用法错误」「运行错误」处理 |
| `--limit` | 默认 30，上限 200；非整数、0、>200 都 exit 2 |
| `--json` | 输出单个对象；**字段顺序不作契约，字段名与类型作契约** |

```json
{"schema_version":1,"query":"架构","vault":"~/Obsidian/Main","exit_code":0,
 "indexed":41,"excluded":0,"index_ms":2.1,"query_ms":0.3,"total_ms":2.8,
 "results":[{"rel":"a.md","title":"架构","rank_class":"title","body_hits":2,
             "mtime_ms":1760000000000,"snippet":"…架构…","start_byte":120,"end_byte":126}]}
```

| 退出码 | 含义 |
|---|---|
| `0` | 搜索完成；**零结果也算成功**；主动排除的 `.icloud` / 软链不算降级 |
| `1` | 库不存在、库根不可读、无法建立可用索引 |
| `2` | 参数错误：空查询、limit 越界、未知选项 |
| `3` | **部分可用**：至少一篇合格 `.md` 因超限/编码/读取失败跳过正文，JSON 必须给 `skipped[{rel,reason}]` |

退出码 3 这个设计比我原来「0 或 2」更实用：它把「搜到了，但有文件没读」和「彻底失败」分开，回归脚本才能断言「跳过而不报错」。

## 12. 使用看板（补 · 1.4.1）

### 12.1 事件结构（与 PRD §11.3 同名同义）

Swift 侧用驼峰，落盘用下划线，映射在一处写死；**字段名是契约**，改名即破坏历史事件可读性。

```swift
struct MetricEvent: Codable {
    let v: Int                  // schema 版本，固定 1
    let ts: Date
    let ev: String              // accepted | drop | open | search | ai | pending | config
    var captureID: String?      // 一次用户动作；批量拖 3 个文件是 1 个 capture
    var noteID: String?         // 与本应用发起的打开事件关联
    var kind: String?           // file | shot | memo | text
    var targetID: String?       // 相对路径加盐哈希前 8 位，不落目录真名
    var bytes: Int?
    var chars: Int?
    var ms: [String: Int]?      // prep / transcribe / ai / write
    var ok: Bool?
    var err: String?            // 只放分类码，不放正文
    var from: String?           // open 事件：after-drop | search | detail
    var ai: AIEvent?
    var app: String?

    enum CodingKeys: String, CodingKey {
        case v, ts, ev, kind, bytes, chars, ms, ok, err, from, ai, app
        case captureID = "capture_id"
        case noteID    = "note_id"
        case targetID  = "target_id"
    }
}
```

**写入点必须覆盖五条入口**（只写 GUI 结束点会漏掉截图、灵感、CLI）：`accepted` 在 coordinator 接受动作时；`drop` 在唯一归档出口的终态；`open` / `search` 在各自的动作回调；`pending` 在 `PendingStore` 的增删。

三条实现约束：

1. **调用线程只做值传递**：主线程只构造结构体并 `enqueue`，JSON 编码与追加落盘在 `global(qos: .utility)` 上做，缓冲上限 256 条、超限丢最旧并记一条 `ev=dropped`。这样才真的不占主线程。
2. **写失败一律吞掉**：落库已经完成，事件写失败不影响任何返回值。
3. **轮转复用同一套**：把 `DiagLog` 里的「按大小轮转」抽成 `RotatingFileWriter`（size 上限、`.tmp`→`rename`、0600），`DiagLog` 与 metrics 共用，不再各写一份。

### 12.2 聚合口径

```swift
struct Distribution {          // 不画漏斗，只画状态分布
    let written: Int           // 已入库
    let pending: Int           // 待归档
    let failed: Int            // 失败
    let cancelled: Int         // 已接受但被用户取消
}

struct Latency {
    let n: Int
    let median: Int            // 永远可给
    let p95: Int?              // n >= 30 才有值；n < 30 为 nil
    let max: Int               // 永远可给
}

struct MetricsSummary {
    let days: [DayBucket]
    let dist: Distribution
    let successRate: Double?   // written / accepted；accepted == 0 时为 nil
    let latency: Latency
    let revisit: Revisit?      // 仅「已满 24h 的 cohort」且排除 after-drop
    let targets: [(id: String, n: Int)]
    let errors: [(String, Int)]
    let ai: (calls: Int, tokens: Int, downgraded: Int)?
    let recent: [MetricEvent]
}

enum MetricsQuery {
    static func summary(events: [MetricEvent], now: Date, days: Int) -> MetricsSummary
}
```

`MetricsQuery` 是**纯函数**（输入事件数组 + 当前时间，输出汇总），自检可以直接喂假事件，不需要磁盘也不需要 GUI。

不做漏斗的理由写在 PRD §11.4：漏斗需要 `accepted → 终态` 的完整生命周期，而首批只保证终态正确；画出来会是假流失。

### 12.3 看板窗口

### 12.4 验收

| 断言 | 方式 |
|---|---|
| 事件 JSON 往返：`capture_id` / `target_id` / `note_id` 的下划线键名不丢、不改 | 自检固定字符串比对 |

## 13. AI 前置处理（补 · 1.5.0）

### 13.1 挂在哪一行代码上（复核后重写）

我原来写「插在 `acceptDone` 与 `Filer` 之间」。**这是错的**，复核第 14 条指出：文字在转写完成后**已经先写进 pending 队列**，之后有两条路会归档同一份结果——UI 的 `acceptDone`，和看门狗 / 启动时的 `MemoArchiveQueue.drain()`。

如果 AI 只挂在 UI 那条路上：看门狗先把原始笔记写掉、pending 消失，UI 随后拿着 AI 结果去写，发现 pending 已不存在，按 1.3.14 的幂等逻辑静默跳过 → **这一篇永远是原文，AI 白跑一场**，而看板上还会显示「AI 成功」。

所以挂载点必须收拢到**唯一出口**。但只有「唯一出口」还不够——**`decoration == nil` 同时代表三种情况**（还没试、试了失败、主动跳过），用它当幂等键会在落库失败重试时重复调用模型、重复计费。必须用显式状态：

```swift
enum AIState: String, Codable {
    case off          // 未启用 AI（全局关闭或该 profile 被停用）
    case pending      // 待处理：drain 到这里要调用模型
    case done         // 已产出 decoration，直接用，不再请求
    case skipped      // 试过但降级（网络/401/非 JSON/护栏），用原文，不再重试
}

struct PendingMemo {
    // …既有字段不动…
    var aiState: AIState = .off
    var decoration: NoteDecoration?   // 只有 aiState == .done 时非 nil
}
```

```
MemoArchiveQueue.archive(m)            ← 唯一归档出口（UI / 看门狗 / 启动补写都走这里）
   ├─ claim(id)                        串行队列内认领
   ├─ if m.aiState == .pending {       ← AI 只在这一处、只在这个状态触发
   │      m.decoration = await AI.decorate(m.text)   // 成功 → .done；任何失败 → .skipped
   │      m.aiState = (m.decoration == nil) ? .skipped : .done
   │      PendingStore.save(m)         ← 先落盘再写笔记：进程崩了也不会重跑
   │  }
   ├─ Filer.memo(text:decoration:)     原有的原子写入
   └─ PendingStore.remove(id)
```

| 规则 | 原因 |
|---|---|
| 用 `aiState` 而不是 `decoration == nil` 做幂等键 | `nil` 有三种含义；状态机只有一种含义。落库失败后重新 drain 时，`.done` 与 `.skipped` 都直接跳过，**不会重复请求、不会重复计费** |
| `.skipped` 也要持久化 | 否则断网期间每次 drain 都会再等 12 秒，队列越积越慢 |
| 迁移：既有 pending 文件没有该字段 | 解码默认 `.off`，行为与 1.3.15 完全一致（老队列不因升级而突然开始调模型） |
| AI 只能在 `archive()` 内被调用 | UI 与看门狗共用一条路径，不存在「谁先写谁赢」 |

**代价**：AI 的等待时间现在发生在归档队列里，而队列是串行的——一次慢请求会挡住后面的补归档。因此 `MemoArchiveQueue.drain(limit:)` 的 limit 要与 AI 超时联动，且 AI 期间必须继续发心跳（见 §13.3）。

### 13.2 分层

```
AIRequest(text) ──► AIPipeline
                      ├─ Prompt.build(text)         纯函数，可自检
                      ├─ AITransport.send(...)      协议：真实现走 URLSession，自检走 StubTransport
                      ├─ AIResponse.parse(json)     纯函数，容错解析
                      ├─ AIResponse.validate(→NoteDecoration?)  纯函数
                      └─ Guard.check()              计数/熔断
```

`AITransport` 是协议而不是直接用 `URLSession`，目的只有一个：**让断网、401、非 JSON、超时这四种失败都能在自检里复现**，不依赖真网络。

### 13.3 请求预算与协议边界（复核后收紧）

| 项 | 规则 |
|---|---|
| 总预算 | **绝对 12 秒**：连接 3 s + 首字节 5 s + 读 4 s；超时即降级，不再重试第二次 |
| 重试 | 只对「请求还没发完」的网络类错误重试 1 次（DNS / 连接失败）；已发出的请求**不重试**，避免重复计费 |
| 响应体 | 上限 256 KB，超限立即 cancel；拒绝 `text/event-stream`（我们不做流式，遇到 SSE 直接判协议不符） |
| 重定向 | 不跟随跨主机重定向；若必须跟随，剥掉 `Authorization` |
| 代理 | 沿用系统代理设置，但在设置页写明「会走系统代理」，避免用户以为直连 |
| 并发 | 归档队列串行，天然只允许一次在飞；不做并发请求 |

**为什么砍掉流式**：流式只改善「等的时候能看到字」，而我们的场景是「说完话等几秒出笔记」，界面本来就有进度环。为它引入 SSE 解析、断流重连、部分 JSON 合并，收益为零、风险很大。

- 远程只允许 `https`；`http` 只允许 `127.0.0.1` / `localhost` / `::1`
- 所有对外输出（`--ai-test` 的 JSON、日志、错误弹窗、问题报告模板）统一走一个 `redact(url)`：只保留 `scheme://host[:port]/path`，其余全部抹掉
- 服务端返回体一律不落日志、不进弹窗；错误只保留分类与状态码

`--ai-test` 输出：

```json
{"profile":"local-qwen","base":"http://127.0.0.1:11434/v1",
 "steps":[{"n":"reach","ok":true,"ms":12},
          {"n":"auth","ok":true,"ms":210},
          {"n":"complete","ok":true,"ms":640,"model":"qwen2.5:7b"}],
 "verdict":"ok"}
```

### 13.5 熔断与护栏

- 单日调用 ≤ 200：计数**独立原子持久化**（`ai-state.json`，`.tmp` → `rename`）。**不能用 metrics.jsonl 当事实来源**——埋点规则是「写失败要吞掉」，拿它做执行控制会在磁盘满时失准
- 连续失败 3 次 → 暂停 10 分钟，菜单图标加小黄点，点开提示原因
- 输入 > 6000 字 → 截断并在事件里标 `truncated: true`
- 模型返回非 JSON → **不重试**，直接降级。理由：请求已经发出，重试只会多计一次费；提高成功率靠 `response_format: json_object` + 更严的 prompt，而不是重发

### 13.6 验收

| 断言 | 方式 |
|---|---|
| `Prompt.build` 含分隔符、超长被截断、不吞换行 | 自检 |
| `parse` 能处理 ```json 包裹、前后多余文字、单引号 | 自检 |
| `validate` 过滤超长标签、少于 3 个则丢标签、target 不存在则忽略 | 自检 |
| 四种失败均降级为「无 decoration 入库」 | StubTransport 注入 |
| 熔断：第 4 次连续失败后不再发请求 | StubTransport 计数 |
| Keychain 存取不落 UserDefaults | 自检（临时 service 名） |
| 事件里只有 host 与状态码，无 Key、无正文 | 自检扫日志 |
