为什么不是一次做完

拆文件放在最后，不是因为它难，而是因为它会把前三项的 diff 全部沉进「移动过的代码」里， review 与回归成本翻倍。而拆文件本身不提升任何运行时性能——多文件仍编译成同一模块， 真正的性能只能靠 §性能 里那九条调用链修复。

// statusItem.menu 永久置 nil，菜单按需弹——不反复挂摘、不调 performClick
private func buildStatusItem() {
    statusItem = NSStatusBar.system.statusItem(withLength: NSStatusItem.variableLength)
    if let b = statusItem.button {
        b.target = self
        b.action = #selector(statusItemClicked(_:))
        b.sendAction(on: [.leftMouseUp, .rightMouseUp])
    }
    statusItem.menu = nil
    rebuildMenu()                       // 只刷新 popupMenu 缓存
}

@objc private func statusItemClicked(_ sender: NSStatusBarButton) {
    guard let event = NSApp.currentEvent else { return }
    switch event.type {
    case .leftMouseUp:  togglePanel()                        // 按模式分派
    case .rightMouseUp: presentMenu(with: event, in: sender)
    default: break
    }
}

这条改动的三个隐藏耦合

① 面板右键现在直接读 statusItem.menu（main.swift:3391-3394），置空后会静默失效，必须改成共享菜单对象； ② 用户开着「窗口置于底层」时，下拉面板会压在所有窗口后面 ≈ 点不出来，dropdown 必须强制 .floating； ③ DropView.hitTest（main.swift:3020）把整块区域都交给自己，1.4.0 的搜索框会「看得见、点不动」。

文件常驻内存，输入即比对；从上往下算，整条链路 3 毫秒。

淘汰 FTS5 的理由，不是「够快了」

引入 FTS5 意味着多一个 DB 生命周期：建库、迁移、损坏后重建、以及「索引和真实文件不一致」这一类只在线上才会暴露的问题。 它换来的是 3 ms → 1 ms，用户感知不到。Spotlight 则反过来：中文两字召回是硬伤（按词切分）， 未索引外置盘直接失效——但它能搜到 .pptx 正文，这是自建索引做不到的，所以留给 1.5.1。

埋点的三条硬规矩

① 绝不记正文——只记长度、字节数、目标目录，日志里出现笔记内容就算缺陷； ② 埋点不能拖慢主流程——先落库再记事件，事件写失败一律吞掉，绝不因为统计让一次投递失败； ③ 版本号必须有——老事件永远可读，新字段只增不改，否则三个月后图表会无声错位。

挂载点只有一个：归档队列的出口

不能挂在 UI 的「收到转写结果」上。因为文字转完已经先落进 pending 队列，看门狗与启动补写也会归档同一份结果—— 只挂 UI 会出现「看门狗先把原文写了，UI 拿着 AI 结果去写时 pending 已不存在，被幂等逻辑静默跳过」， 结果是这篇永远是原文，看板还显示 AI 成功。所以只能收在 MemoArchiveQueue.archive() 里， 并把 decoration 写回队列文件：重启后直接复用，不重跑、不重复计费。

一条不能破的红线

AI 环节不能导致「这次投递失败」。所有失败都收敛成「原文入库」，与 1.3.15 行为一致。 实现上它只挂在 MemoArchiveQueue.archive() 里、Filer 之前，UI 与看门狗共用这一条路； 状态用显式四态 AIState（off / pending / done / skipped）而不是 nil——nil 说不清「没试过」「失败」「跳过」，落库失败重试会重复计费；因此 1.3.14 建立的原子写入、pending 队列、看门狗全部继续有效。
